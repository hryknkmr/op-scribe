# 0002. 伏せる規則のレビューが収束しなかった真因と対策

- 状態: 採用（2026-10-31）。決定したのは、真因の分析、進め方の「分けて作り直す」、対策 1〜3 と 6。対策 1〜3 は作り直しの最初の PR で入れた（[ADR 0003](0003-privacy-guarantee-matrix.md)、`shared/payload.js`）。対策 4・5 は案で、後の PR のレビューで確定する。
- 日付: 2026-10-31
- 関係: PR #6、[ADR 0001](0001-commercial-environment-policy.md)

## 事実

- PR #6 に Codex のレビューを 38 ラウンドかけた。BLOCKER と HIGH は 0 にならなかった。
  - 1〜20 ラウンド目: 全環境で値を残す方針。
  - 21 ラウンド目以降: ADR 0001 の、商用環境だけ厳格にする方針。
- 指摘は毎ラウンド、前のラウンドとは違う箇所に出た。同じ穴が直らずに残ったことはほとんどない。
- 38 ラウンドの BLOCKER と HIGH（およそ 90 件）を種類で分けると、次のとおり（件数は目安）。

| 種類 | おおよその割合 | 例 |
| --- | --- | --- |
| A. 値の形の検出漏れ（表記の揺れ） | 約 5 割 | 区切り文字（`.` `*` `–`）、他の文字体系の数字、多重エンコード、壊れた `%`、URL の書き方（`https:host`、`//host`、バックスラッシュ）、メールの書き方（引用符、domain literal、ドットの無いドメイン）、不可視文字 |
| B. キー名の語彙の漏れ | 約 2 割 | `otp1`、`cvv2`、`client_secret`、`csrf`、`auth_key`、`ssn`、`APIキー`、`PINコード`、`credit_card` |
| C. 層ごとの判定の食い違い | 約 2 割 | content script と worker、worker と最終検査、最終検査と受信サーバ、記録開始時と現在の設定、伏せ字を信用する範囲 |
| D. 直前の修正による退行 | 5 件前後 | 2・11・35 ラウンド目の BLOCKER または HIGH、ID 判定の取りこぼし、規則の順序の入れ替え |
| E. 方針の解釈の揺れ | 数件 | 選択欄の値（8 ラウンド目と 17 ラウンド目で逆の指摘）、`session`、旧設定の利用者の移行 |

## 真因

1. **作りと約束が合っていない。**
   - 値を残したうえで、パターン（拒否リスト）で伏せる作りにしている。入力の書き方は無数にあるので、パターンで全部を見つけることはできない。
   - それなのに文書では「メールアドレスは一部を伏せる」「カード番号は完全に伏せる」と保証している。
   - 保証と書いた以上、抜けが 1 つ見つかるたびに HIGH になる。「HIGH が 0 になるまで回す」という収束の条件は、この作りでは満たせない。種類 A と B のほぼすべてがここから来ている。
2. **何を想定し、何を想定しないかが決まっていない。**
   - どの文字体系・区切り・エンコード・URL の書き方までを対象にするかが書かれていない。
   - そのため、レビューのたびに範囲が広がる。他の文字体系の数字や Unicode のダッシュ、受信サーバの型、Markdown の注意書きなどが、毎回新しく範囲に入った。
3. **層の間で、判定を共有するところと独立させるところが整理されていない。**
   - content script と worker は、欄の種類や商用かどうかをそれぞれの手がかりで判定しており、食い違いが生まれる（種類 C）。
   - 一方、最終検査（`finalScan`）と受信サーバは、伏せる処理と同じ判定（`scrubText`）を使っている。独立した検査に見えて、伏せる処理の見逃しをそのまま見逃す（下の Codex の指摘）。
   - 当初は「層ごとに自前の判定を持っている」と書いたが、最終検査と受信サーバについては Codex の検証で誤りと分かったので、上のとおり改めた。
4. **直し方が場当たり的で、守る仕組みが無い。**
   - 指摘を 1 件ずつ、その場の規則の追加で直した。
   - #6 にはテストが 79 件あったが、指摘を受けた箇所ごとの例に留まる。38 ラウンドの反例を体系的に集めた回帰用の資料も、どんな入力でも成り立つべき性質の検査も無い。
   - そのため、直した箇所の周りで退行が起きた（種類 D）。
5. **レビューに判定の物差しを渡していない。**
   - 経緯を渡さない最終ラウンドは、盲点を見つけるのには効いた。
   - 一方で、想定する脅威の範囲と重大度の基準を渡していない。そのため、範囲外の抜けも HIGH と判定され、方針の解釈も揺れた（種類 E）。

## Codex による独立した検証（2026-10-31）

私の結論（この ADR の上の部分）は渡さず、38 ラウンドの全文と経緯の事実だけを渡して、真因を分析させました。全文は作業メモ `tmp/cxm6/rootcause-output.txt` にあります（リポジトリには入りません）。

- **一致した点**
  - 開いた入力空間に対して閉じた保証を書いたこと（真因 1）。
  - 対象範囲と停止の条件が決まっていなかったこと（真因 2・5）。
  - 反例を 1 件ずつ直したこと（真因 4）。
  - 件数の分け方は異なりますが、BLOCKER・HIGH は約 90 件。方針を変えた後は、1 ラウンドあたり約 3.0 件から約 1.8 件に減りました。
- **Codex が新たに挙げた点**
  - **最終検査が、伏せる処理と同じ判定を使っている。** 伏せる処理が見逃すものは、最終検査も受信サーバも見逃します。三段に見えて、判定は一段です。そのため、私の案の対策 3（最終検査を「もう一度伏せても変わらないこと」にする）は、この共通の盲点をかえって強めます。
  - **伏せた状態を、ページ由来の文字列と同じ形で表している。** `[[secret]]` や `ab**23` を文字列で持つので、出どころが失われます。そのため、ページがそれらしく作った値を信用してしまう、二重に伏せる、伏せ字の中に値を埋め込まれる、といった指摘が繰り返されました。規則を足しても直りません。
  - **1 ファイル（`shared/sanitize.js`、324 行から 863 行）に、正規化・語彙・抽出・URL 解析・方針の分岐・伏せ字・出口検査が集まっている。** 規則の順序に意味がある作りでもあります。
  - **ADR 0001 は攻撃面を消さず、分岐を増やした。** 値を残す経路が多く残り、そこに商用かどうか・設定の固定・移行・サイトへの帰属という新しい状態が加わりました。

## 対策（Codex の検証を受けて改めた案）

1 と 6 はオーナー承認済みの決定。2 と 3 は作り直しの最初の PR で中身を確定して入れた。4 と 5 は案で、後の PR で中身を確定する。

| # | 対策 | 効く真因 | 中身 |
| --- | --- | --- | --- |
| 1 | 保証を分けて固定する（オーナー承認済み） | 1・2 | 構造で保証するものと、できる限り見つけるものを表にし、範囲外のものも書く。後者の漏れは既知の限界とし、レビューでは MEDIUM |
| 2 | 伏せた結果を、型の付いた値で持つ | 真因 3、Codex の「伏せた状態の表し方」 | `{ treatment: 'redacted', kind: 'secret' }`・`{ treatment: 'length', length: 12 }`・`{ treatment: 'partial', kind: 'email', display: 'a***@e***.com' }` のように持ち、Markdown などの文字列にするのは最後だけにする。ページが作った `[[secret]]` は、ただの文字列として扱う |
| 3 | 出口は独立した構造の検査にする（旧案の「もう一度伏せる」は採らない） | 真因 3、Codex の「共通の盲点」 | 出口と受信サーバは、送信データの形・型・扱いの印（上の型の付いた値）を検査する。伏せる処理とは別の判定にする。文の中のパターンの再検査は「できる限り」の側に置く |
| 4 | 正規化・URL 解析・キーの語彙を別の部品にする | 真因 3、Codex の「1 ファイルへの集中」 | 入口で 1 回だけ正規化し、正規化した後の値だけを分類する。規則の順序に頼らない |
| 5 | 受け入れの表と、性質の検査 | 真因 4 | 「環境 × 経路 × 値の種類 × 変形」の組ごとに、残す・一部伏せる・全部伏せる・拒否のどれか 1 つを決めてテストにする。90 件の反例を回帰用の資料にし、変形を生成して性質を検査する |
| 6 | レビューに、固定した保証の表と重大度の基準を渡す（オーナー承認済み） | 真因 5 | 範囲内の違反は BLOCKER または HIGH。範囲外の実害は、ADR の既知の限界か後続の Issue にする。収束の条件は「固定した表の範囲で BLOCKER・HIGH が 0、資料と性質の検査が通る、最後の修正の後に確認済み」。資料と性質の検査は対策 5 で作るので、対策 5 を入れるまでは「資料と性質の検査が通る」を除いた条件で判定する |

## 進め方（「分けて作り直す」はオーナー決定。順序は案）

Codex は、今の PR をそのまま小さく直してマージするより、分ける方が安全としています。

1. **保証の表を固定する（対策 1）**: ADR・PRIVACY.md の書き換え。表は、次の 2 の最初の PR（型の付いた値と出口の構造の検査）で、送信データの形の定義と一緒に作る。送信データのすべての欄が表のどれかの行に当たることを、テストで確かめる。
   - 表だけを文書で先に固めようとしたところ（#10）、3 ラウンド続けて「表に無い欄がある」「ADR 0001 と食い違う」という HIGH が出た。欄の一覧がコードにしか無いので、文書だけでは網羅を確かめられないと判断した（2026-10-31 オーナー決定）。
2. **分けた PR で作り直す（対策 2〜5）**: 型の付いた値と出口の構造の検査、URL・ホストの正規化、「できる限り」の検出、の順。
3. **固定した表に照らしてレビューする（対策 6）**。

いまの #6 の作業（商用環境の扱い、`classifyKey`、テスト 79 件）は、作り直しの土台として引き継ぐ。回帰用の資料（対策 5）は、このテストとは別に、38 ラウンドの反例から作る。
