# 0006 長い記録は、保存して新しい記録で続ける（手元の上限の手前で知らせる）

- 状態: 提案
- 日付: 2026-11-05（2026-11-08 に作り直し）
- 関連: ADR 0003（保証の表）、ADR 0005（書式 A・B）

## 背景

記録は `chrome.storage.session`（メモリだけ。ブラウザを閉じると消える）にあり、1 つの記録は 500 ステップ（`LIMITS.steps`）・6 MiB（`LIMITS.storeBytes`）までです。これを超えると古いステップから消えて `trimmed` が付き、長い探索テストでは始めの方の操作が残りません。上限を上げると、メモリの負担がそのまま増えます。

## 検討して、やめたこと

上限を超えて 1 つの記録を続けるために、次の 2 つの形を検討しました。どちらも、外部のレビューを何回重ねても新しい穴が見つかり、収束しませんでした。

1. **記録の途中で区切りを送信先に送り、受け取れたら手元から消す**（送信先は手元の中継、その先に Notion）。拡張・中継・Notion の 3 か所で「1 回だけ確実に届けて、手元から消す」を成り立たせる必要があり、予約・取り消し・再送・冪等の状態が多くなりすぎた（3 ラウンド）。
2. **区切りをファイルに保存し、保存の完了を確かめてから手元から消す**（`downloads` 権限、通し番号、台帳、送信データ v6）。記録を続けたまま、非同期の保存の完了を待って手元から消すため、保存のあいだに届くステップ・テスターの変更・上限・パネルの再起動との組み合わせごとに、固定・ロック・照合の仕組みが要った。直すたびに仕組みが増え、その仕組みに新しい穴が見つかった（10 ラウンド）。

真因は、「記録を続けたまま、記録の一部だけを外へ出して手元から消す」ことでした。1 つの記録の中に「出したもの」と「手元にあるもの」が混ざるため、その境目の状態を正しく保つ仕組みが要ります。あわせて、出したあとの記録全体の書式 A・B をどう作るかも決めなければなりません。区切りのファイルを Notion に書く CLI も、重要度が低いわりに判断の難しい論点が多いため作りません（オーナー判断 2026-11-08）。

## 決めたこと（オーナー判断 2026-11-08・11-10）

**記録を区切らない。上限の手前で知らせ、今の記録を保存して、続きを新しい記録で始められるようにする。**

1 つの記録は、今と同じく開始から停止まで手元にあり、書式 A・B・JSON・Markdown・Gherkin・Playwright の下書きは今のまま 1 つの記録から作ります。長い探索テストは、複数の記録に分かれます（ADR 0005 の「複数の記録を束ねるのは、人が別の場所で行う」のとおり）。

### 上限の手前の知らせ

- 記録中に、ステップ数（500）か記録の大きさ（6 MiB）のどちらかが上限の 8 割以上になったら、サイドパネルに知らせを出す（「記録が上限に近づいています。上限を超えると、一部のステップが記録から消えるか、記録されなくなります（ページからの申告・通知・遷移が先）」）。知らせは記録を止めず、プレビューも開かない。8 割を下回れば（ステップを消したときなど）消す。
- 割合の元の値は、worker が記録を `chrome.storage.session` に書く直前（最後の `fitRecord` のあと）に一度だけ決め、記録の欄 `usage`（`{ steps, bytes }`）に入れる。`bytes` は、`usage` を除いた記録を `fitRecord` と同じ数え方（UTF-8 のバイト数）で数えた値。`fitRecord` は、前の `usage` を除いて記録を数え、`usage` が取りうる最大の大きさ（`steps` が `LIMITS.steps`、`bytes` が `LIMITS.storeBytes` の桁数と、欄の名前・区切りを含む固定値 `USAGE_RESERVE_BYTES`）を見込んで上限に収める（`usage` を足したあとも 6 MiB 以下。ADR 0003）。パネルは記録を読むたびに、`usage` と `LIMITS` から割合を出す。`usage` は送信データに入れない（`buildPayload` は許可リストで作るので入らない。テストでも確かめる）。
- 上限のほかに、サイトごとのページからの申告の上限（ADR 0003）でもステップが落ちる。これは 8 割の知らせでは予告しない。代わりに、記録に `trimmed` が付いているあいだは、どの上限でも「記録の一部が上限で消えました」と知らせ、同じボタンを出す（`trimmed` は戻らないので、出し続ける。パネルを閉じていたあいだに付いても、開けば出る）。
- 知らせには、ボタン「保存して、続きを新しい記録で始める」を付ける。

### 保存して、続きを新しい記録で始める

ボタンは、今ある操作を順に呼ぶだけです。worker に新しい状態は持ちません。パネルは、どの記録に対する操作かを、その記録の ID でメモリに持ちます（パネルを開き直したら持っていない）。

1. パネルに、今の記録への、記録へ送っていない判定の入力（判定のフォームで「判定を保存」を押していないもの）があれば、先に「保存していない判定があります」と出し、保存するか捨てるかを選ばせる。保存するなら 1 つずつ保存し、それぞれ worker の返事と記録の読み直しを待つ。1 つでも保存に失敗したら（`NO_REF`・`NO_ACTUAL` など）そこで止め、停止にもプレビューにも進まない。失敗した入力は、テスターが直すか「捨てる」を選ぶまで残す。
2. 記録中なら、今の「停止」と同じく記録を止める（`recordingId` 付き。「やっていないこと」を書く欄は今の停止と同じ）。
3. 止めた記録の JSON のプレビューを見せ、**プレビューの中の「保存」ボタンで**保存する。保存するのは、プレビューした送信データのバイト列そのもの。保存の直前に、今の送信と同じく設定と記録を読み直し、プレビューのときと同じ送信時刻・簡易手順・環境で送信データを作り直して、**整形した JSON の全文がプレビューしたものと同じか**と、出口の検査（`checkPayload` と `finalScan`）を確かめる（記録 ID と `revision` は早く断るためだけに使う。判定・停止・ツール一覧の変更は `revision` を進めないので、それだけでは見逃す）。合わなければ保存せず、「プレビューのあとに記録が変わりました」と出してプレビューし直させる（プレビューのあとに別のパネルで判定を変えた・別の記録を始めた、などのとき、確かめていない中身や別の記録を保存しないため）。必要なら、テスターはここで書式 A・B やほかの書き出しも作る（今の停止したあとの記録と同じ）。
4. テスターが「続きを始める」を押すと、パネルは開始の入力欄（対象と範囲・対象のバージョン）を、続きのための状態（前の記録の ID を持つ）で表示する。ここではまだ始めない。
   - 「対象と範囲」と「対象のバージョン」の欄には、前の記録を**このパネルで**始めたときにテスターが書いた生の文を、パネルがメモリに持っていれば入れておく。パネルはその文を、始めた記録の ID と組で持ち、その記録の続きを始めるときにだけ使う（パネルを開き直したら持っていない。別の記録には使わない）。記録に保存した伏せたあとの文（runs）から入力の文を作り直すことはしない（伏せ字を入力として戻すと、意味と伏せた数が食い違うため）。持っていなければ空。テスターは直せる。
   - パネルは、前の記録の ID を「対象と範囲」に書き足すことを勧める文を出す（自動では書き足さない）。
5. テスターが入力欄を直して「記録開始」を押すと、下の「記録を始めるとき」のとおりに始める（前の記録の ID は、4 で持った ID）。開始の画面は、今の開始と同じくアクティブなタブ。

### 記録を始めるとき（今の開始ボタンも同じ）

止めた記録が手元にあるときは、どのボタンから始めても、同じ確かめと照合をします（今の「記録開始」ボタンも含む。今は、止めた記録を確かめずに上書きできる）。

- パネルは毎回「前の記録は手元から消えます。保存したファイルがあるか確かめてください（拡張は保存できたかを確かめられません）」と確かめる。保存したかどうかで出し分けない（拡張は保存の完了を知らず、押したことを覚える状態も持たないため）。この確かめは、権限の要求（`chrome.permissions.request` はクリックの中で同期して始める必要がある）より前の、別のクリックで行う。
- 確かめたら、`START` に、パネルが表示している前の記録の ID（`expectedPrevious`）を付けて送る。worker は書き込みの列の中で、今の記録がその ID で、止まっているときだけ新しい記録を始める。記録が無いときは `expectedPrevious` 無しで始められる。記録があるのに `expectedPrevious` が無い・合わない・記録中のときは、始めずに断り、パネルは記録を読み直して「別の記録が始まっています」などと出す（別のパネルの開始と重なっても、確かめていない記録を消さない）。
- `START` の成功の返事に、新しい記録の ID を入れる。パネルは、送った生の対象と範囲・対象のバージョンを、この ID とだけ組にする（返事を待つあいだに別のパネルが始めた記録と取り違えない）。
- 今の「記録開始」は、記録中の記録を止めて新しい記録を始められる。これも同じく、止める前に確かめ、`expectedPrevious` を付ける。

### 変えないもの

- 送信データの形（`shared/payload.js` の `SHAPE`）、ADR 0003 の表、受信サーバ、書式 A・B は変えない。
- 上限（500 ステップ・6 MiB・サイトごとの申告の数）と、上限を超えたときの動き（ページからの申告・通知・遷移を先に落とし、落とせなければ新しいものを記録しない。`trimmed` を付ける）は変えない。知らせを見ても続けた記録は、今と同じく欠ける。

## 既知の限界

- 長い探索テストは、複数の記録とファイルに分かれる。つなぐのは人（「対象と範囲」に前の記録の ID を書く、など）。
- 前の記録を保存できたかどうかを、拡張は確かめない。止めた記録があるときは、どのボタンから新しい記録を始めても、毎回テスターに確かめる（今の開始ボタンの動きを変える。オーナー判断 2026-11-10）。
- 知らせは 8 割以上のあいだ出続ける。テスターが続けると、今と同じく上限でステップが欠ける。サイトごとのページからの申告の上限は予告せず、消えたあとに知らせる。
- 前の記録の最後の操作の結果（遷移・通知）が、止めたあとに届くと、どちらの記録にも入らないことがある（今の停止と同じ）。

## 実装の順

1. worker: `usage`（最後の `fitRecord` のあとに一度決める。`fitRecord` は前の `usage` を除いて数え、`USAGE_RESERVE_BYTES` を見込む）と、`START` の `expectedPrevious`（記録があるときは必須）と返事の記録 ID。テスト（record・worker。`usage` が送信データに入らないこと、8 割ちょうどの境目、予約の境目で 6 MiB を超えないこと、`expectedPrevious` が無い・合わない・記録中のときに始めないこと。今の「続けて START すると前の記録が置き換わる」テストは、この決まりに合わせて直す）。
2. サイドパネル: 8 割と `trimmed` の知らせ、「保存して、続きを新しい記録で始める」（保存していない判定の確かめ → 停止 → プレビューの中の保存（全文を作り直して照合）→ 続きの入力欄 → 確かめ → `expectedPrevious` 付きの開始）。今の開始ボタンにも確かめと `expectedPrevious`。E2E（上限を小さくした設定で、知らせが出て、保存して新しい記録が始まる）。
3. README（長い探索テストの進め方）。

## 決めなかったこと

- 1 つの記録の途中で、一部だけを外へ出して手元から消すこと（上の「検討して、やめたこと」）。
- 区切りや記録を Notion などへ書く道具（オーナー判断 2026-11-08）。
- 前の記録と新しい記録を、送信データの欄（前の記録の ID など）でつなぐこと（欄を足すと ADR 0003 の行と検査が要る。今は人が「対象と範囲」に書く）。
- 上限を上げること。
