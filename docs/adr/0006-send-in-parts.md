# 0006 記録を区切りごとに送る（手元の上限を超えて記録を続ける）

- 状態: 提案
- 日付: 2026-11-05
- 関連: ADR 0003（保証の表）、ADR 0005（書式 A・B、期待結果と判定）、`tools/receiver.mjs`

## 背景

記録は `chrome.storage.session`（メモリだけ。ブラウザを閉じると消える）にあり、1 つの記録は 500 ステップ（`LIMITS.steps`）・6 MiB（`LIMITS.storeBytes`）までです。これを超えると、古いステップから消えて `trimmed` が付きます。長い探索テストでは、始めの方の操作が残りません。

上限を上げると、メモリの負担がそのまま増えます。そこで、記録の途中で、そこまでのステップを送信先に送り、送れたら手元から消して記録を続けられるようにします。送信先の例は Notion の DB です。

## 決めたこと（オーナー判断 2026-11-05）

- **送る前に必ずプレビューを見る**今の約束は変えない。確認なしで自動で送り続けることはしない。
- 区切って送るきっかけは、手動の「ここまでを送る」と、上限の 8 割（ステップ数か大きさのどちらか）に達したときのパネルでの知らせ。知らせはプレビューを自動で開かない。
- 区切りは、**最初の未判定の期待結果の手前まで**にする。送ったあとに判定を付け直す仕組みは持たない。
- 書式 A・B（バグチケット・実施記録）のために、送った区切りの**小さな要約**を手元に残す。
- Notion へは、拡張から直接は書かない。手元の中継（`tools/receiver.mjs` を拡張したもの）が、受信の検査を通したあとに書く。トークンは中継の環境変数に置き、ブラウザには残さない。拡張の送信は汎用の `POST` のまま。
- Notion の DB は、**区切り 1 つを 1 行**にする。記録 ID で束ねる。

## 区切り

区切りは、手元に残っているステップの先頭から、決めた位置までの連続したステップです。

- 終わりの位置は、テスターが「ここまでを送る」を押した時点の最後のステップ。ただし、次の規則で前に寄せる（後ろへは延ばさない）。
  1. **最初の未判定の期待結果の手前まで**。期待結果は、テスターがサイドパネルで書いた、種類の無いメモ（ADR 0005 の `isExpectation`）。判定（`verdict`）の無いものが未判定。ページからの申告（`source: agent`）は判定を持たないので数えない。
  2. 区切りの最後が操作（`click`・`key`・`tool`）で、その直後の遷移がその操作の結果（`followsOperation`）にあたるなら、遷移も区切りに入れる。操作の直後の通知（`notice`）も、次の操作の手前まで区切りに入れる。操作とその結果を別々の区切りに分けると、手順の文が「遷移する」から「開く」に変わるため。1 で前に寄せた結果、この規則で延ばす先が未判定の期待結果を越えるときは、操作の手前まで寄せる。
- 区切りが空になるとき（先頭が未判定の期待結果のとき）は送れない。パネルは「先に判定を付けてください」と、その期待結果を示す。
- 記録を止めたあとの「残りを送る」は、最後の区切り（`final: true`）。最後の区切りにも 1 の規則は当てはまる。未判定が残っていれば、最後の区切りは送れない（判定するか、その期待結果を消す）。

## 送信データ（v6）

送信データを v6 に上げ、`recording.part` を足します（ADR 0003 に M6 の行を足してから実装する。下の「ADR 0003 に足す行」）。

```json
"recording": {
  "id": "rec-…",
  "part": { "index": 2, "from": 181, "final": false },
  "steps": [ { "n": 181, … }, … ],
  …
}
```

- `part.index`: 区切りの番号。1 から。同じ記録で送った順に増える。
- `part.from`: この区切りの最初のステップの、記録全体での番号。`steps[].n` は `from` から 1 ずつ増える（今は 1 から振り直している）。
- `part.final`: 記録を止めたあとに送った、最後の区切りなら `true`。
- `part` が無い送信データは、今と同じく記録全体（v5 以前と同じ意味）。区切りを 1 つでも送った記録は、残りも区切りとしてだけ送れる（全体の送信は使えなくなる）。
- そのほかの欄は今と同じ作り方で、次の違いがある。
  - `startUrl`・`reproduction`（Markdown・Gherkin）は、その区切りのステップだけから作る。2 つ目以降の区切りの Gherkin には、`Background` の前に「区切り N の続き（ステップ M から）」というコメントを入れる。
  - `endedAt`・`notTested` は最後の区切りにだけ入る（今と同じく、止めたあとに付くため）。`scope`・`targetVersion` はどの区切りにも入る。
  - `privacy.redactions` と `hostsAliased` は、記録の始めからの累計。受け取る側は、最後に受け取った区切りの値を使う。
  - 別名（`site-N.invalid`）の対応表は、送ったあとも手元に残す。区切りをまたいでも、同じホストは同じ別名になる。
  - `trimmed` は記録全体の印のまま（どの区切りにも、その時点の値が入る）。

### 出口の検査

区切りの送信データにも、今の出口と同じく `checkPayload` と `finalScan` をかける。`checkPayload` は v6 で次も確かめる。

- `part.index`・`part.from` は 1 以上の整数、`final` は真偽値。
- `steps[].n` が `from` から欠けずに続いている。
- `final` が `false` なら `endedAt` と `notTested` が無い。
- 区切りの中に、未判定の期待結果が無い。

## 送ったあと手元から消す

送信が 2xx で返ったときだけ、送ったステップを手元から消します。

1. パネルは、プレビューした区切りの送信データと、その元になったステップの要約値（区切りのステップを JSON にしたもののハッシュ）を持っている。
2. 送信が 2xx で返ったら、パネルは worker に `COMMIT_PART`（記録 ID・`index`・最後のステップの番号・要約値）を送る。
3. worker は書き込みの列の中で、今手元にある先頭からのステップが、送ったものと同じか（要約値が一致するか）を確かめる。一致すれば、それらを消し、下の要約を手元に足し、次の区切りの `index` と `from` を進める。一致しなければ（送ったあとにステップを消した・書き換わった）、何も消さず、パネルに「送った内容と手元が違うので消していない」と出す。
4. 送信が失敗したとき・2xx 以外のとき・`COMMIT_PART` の前にパネルが閉じたときは、何も消さない。もう一度送ると同じ `index` になる。受け取る側は、同じ記録 ID と `index` を上書きする（重複しない）。

## 手元に残す要約（書式 A・B のため）

送った区切りごとに、次だけを手元に残します。

- 区切りの `index`・最初と最後のステップの番号・送った日時。
- その区切りの期待結果: `ref`・文・判定・実際の結果・画面（ADR 0005 の「期待結果の位置」の伏せた URL）。
- 画面ごとの数: 伏せた URL の移り変わりと、それぞれの「記録された操作・ツール呼び出し・ページからの申告」の数（ADR 0005 の `screenParts`）。
- 探索メモ（種類のあるメモ）の文と種類。

要約も記録の大きさ（`storeBytes`）に数えます。要約の期待結果と探索メモは、合わせて 500 件までです。超えた分は古いものから消し、`trimmed` を付けます。

### 書式 A・B の作り方

- **実施記録（書式 B）**: 結論・確かめたこと・見つけたこと・画面ごとの数は、要約と手元のステップを合わせて作る。付録（記録したステップ）は手元のステップだけで、その前に「ステップ 1〜M は区切り 1〜N として送信済み」と書く。
- **バグチケット（書式 A）**: NG の期待結果が手元にあるときだけ作れる。再現手順は手元のステップから作り、先頭に「ステップ 1〜M は区切り 1〜N として送信済み。その続きから」と書く。送った区切りの NG は、送信先にあるので、パネルの一覧に出さない。

## 中継と Notion

`tools/receiver.mjs` に、Notion へ書く設定を足します。`NOTION_TOKEN` と `NOTION_DATABASE_ID` を環境変数で渡したときだけ書きます。

- 受け取った送信データに、今と同じ 2 つの検査（`checkPayload`・`finalScan`）をかけ、どちらかで検出があれば 422 を返して書かない。
- 通ったものを `recordings/<記録 ID>/part-<index>.json` に保存し（区切りでない送信は今と同じ）、そのあと Notion に書く。
- **Notion に書けたときだけ 2xx を返す**。書けなければ 502 を返す。拡張は 2xx のときだけ手元から消すので、Notion に届かなかった区切りは手元に残る。
- DB の 1 行が 1 つの区切り。
  - 列: 題（`<記録 ID> #<index>`）・記録 ID・区切りの番号・最初と最後のステップの番号・送信日時・環境（`coverage`）・NG の数・最後の区切りか。列の名前と型は、中継の起動時に DB から読んで確かめ、合わなければ起動しない。
  - 本文: Gherkin と属性表を、コードのブロックで入れる。Notion の上限（1 つの文は 2000 字、1 回の書き込みは 100 ブロック）に合わせて分けて書く。
- 同じ記録 ID と `index` の行がすでにあれば、その行を消して作り直す（再送で重複させない）。
- Notion の速さの上限（平均で毎秒 3 回ほど）に合わせて、中継は書き込みを 1 本の列で順に行い、429 が返れば `Retry-After` だけ待って繰り返す。

Notion は外部のサービスです。Notion に書くと、検査を通った記録がそのワークスペースに残ります。どの DB に書くか、誰が読めるかは、中継を動かす人が決めて確かめるものです（PRIVACY.md に書く）。

## 既知の限界

- 送った区切りは、あとから消せない。送ったあとに「必ず伏せる語」を足しても、送信先には届いている。送る前のプレビューで確かめる。
- 未判定の期待結果を置いたままだと、そこから先は送れない。その間に上限に当たれば、今と同じく古いステップから消える（`trimmed`）。パネルは 8 割の知らせで、未判定があることも示す。
- 区切りをまたいで、期待結果を前の操作に付け直すことはできない（区切りの先頭の期待結果は、前の区切りの最後の操作の結果として扱われない）。
- 送信が 2xx で返ったあと、`COMMIT_PART` の前にパネルを閉じると、手元に残ったまま送信先にも届いている。もう一度送ると同じ番号の区切りになり、受け取る側で上書きされる。
- 中継が 2xx を返したあとに Notion 側で行が消された、などは拡張から分からない。

## 実装の順

1. ADR 0003 に M6 を足す。送信データ v6（`part`、`n` を `from` から、出口の検査）、`shared/record.js` に区切りの位置を決める関数と `COMMIT_PART`（要約値の照合・消す・要約・番号を進める）、worker のメッセージ。テストは `tests/payload.test.mjs`・`tests/record.test.mjs`・worker。
2. サイドパネル: 「ここまでを送る」、区切りのプレビューと送信、2xx のあとの `COMMIT_PART`、8 割の知らせ（未判定があれば示す）。E2E。
3. 書式 A・B を要約と手元のステップから作る（`shared/describe.js`）。
4. 受信サーバ: v6 を受け付け、区切りを `recordings/<記録 ID>/part-<index>.json` に上書きで保存。
5. 中継の Notion 書き込み（DB の確認・分けて書く・上書き・速さの上限）と README・PRIVACY・FORMAT。

## 決めなかったこと

- 区切りを、記録を止めずに自動で送ること（プレビューの約束を変えるので、しない）。
- 送った区切りの判定を、あとから更新して送ること（オーナー判断で持たない）。
- 送信先から区切りを取り戻して、手元で書式を作り直すこと。
