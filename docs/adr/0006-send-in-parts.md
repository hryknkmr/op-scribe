# 0006 記録を区切りごとに送る（手元の上限を超えて記録を続ける）

- 状態: 提案
- 日付: 2026-11-05
- 関連: ADR 0001（商用環境）、ADR 0003（保証の表）、ADR 0005（書式 A・B、期待結果と判定）、`tools/receiver.mjs`

## 背景

記録は `chrome.storage.session`（メモリだけ。ブラウザを閉じると消える）にあり、1 つの記録は 500 ステップ（`LIMITS.steps`）・6 MiB（`LIMITS.storeBytes`）までです。これを超えると古いステップから消えて `trimmed` が付き、長い探索テストでは始めの方の操作が残りません。

上限を上げるとメモリの負担がそのまま増えます。そこで、記録の途中でそこまでのステップを送信先に送り、受け取れたら手元から消して記録を続けられるようにします。送信先の例は Notion の DB で、手元の中継が書きます。

## 決めたこと（オーナー判断 2026-11-05）

- **送る前に必ずプレビューを見る**約束は変えない。自動で送り続けない。
- きっかけは手動の「ここまでを送る」と、上限の 8 割（ステップ数か大きさのどちらか）でのパネルの知らせ。知らせはプレビューを自動で開かない。
- 途中の区切りは**最初の未判定の期待結果の手前まで**。送ったあとに判定を付け直す仕組みは持たない。**記録を止めたあとの最後の区切りだけは、未判定を含めてよい**。
- 書式 A・B（バグチケット・実施記録）は拡張の中だけで作る（ADR 0005 のまま）。そのため:
  - 送った区切りの**小さな要約**を手元に残し、実施記録は記録全体で作る。
  - NG の期待結果を含む区切りは、**送る前にそのバグチケットを作らせる**（下の「区切りのプレビュー」）。送ったあとは、その NG のチケットは作れない。
- Notion へは拡張から直接書かない。手元の中継（`tools/receiver.mjs` を拡張）が、受信の検査を通したあとに書く。トークンは中継の環境変数に置く。拡張の送信は汎用の `POST` のまま。
- 中継は、検査を通した区切りを**中継のディスクに保存できたときに 2xx を返す**。Notion にはその保存から順に書く（書けなかったものは保存に残り、書き直せる）。
- Notion の DB は**区切り 1 つを 1 行**にし、記録 ID で束ねる。

## ステップの通し番号

ステップを記録に足すとき、worker が手元だけで使う通し番号 `seq` を振ります（1 から。記録の中で増えるだけで、消しても振り直さない）。送信データの `steps[].n` は、区切りの送信ではこの `seq` です。

上限で古いステップが落ちても、テスターがステップを消しても、残ったステップの番号は変わりません。送った範囲と手元の照合、区切りの番号、再送の上書きは、すべてこの番号で行います（位置で数えると、落ちたステップの分だけずれて別のステップを送り直してしまう）。

区切りでない送信（今の全体の送信）の `n` は今と同じく 1 からの位置です。

## 区切り

区切りは、手元に残っているステップの先頭から、決めた位置までの連続したステップです。

- 終わりの位置は、**プレビューを作る時点**で決める。基準はその時点の最後のステップで、次の規則で前に寄せる（後ろへは延ばさない）。
  1. 途中の区切りは、**最初の未判定の期待結果の手前まで**。期待結果は、テスターがサイドパネルで書いた種類の無いメモ（ADR 0005 の `isExpectation`）。判定（`verdict`）の無いものが未判定。ページからの申告（`source: agent`）は判定を持たないので数えない。
  2. 最後のステップが人の操作・`key`・`tool` で、その操作から 4 秒（`FOLLOW_MS`）たっていなければ、たつまで待ってから決める（直後の遷移が、操作と別の区切りに分かれないように）。
  3. 区切りの最後が操作で、その直後の遷移がその操作の結果（`describe.js` の `followsOperation`。この判定は `describe.js` だけで持ち、ほかで作り直さない）にあたるなら、遷移も区切りに入れる。操作の後の通知（`notice`）も、次の操作の手前まで区切りに入れる。1 で前に寄せたためにこの規則が未判定を越えるときは、操作の手前まで寄せる。
- 途中の区切りが空になるとき（先頭が未判定の期待結果）は送れない。パネルは「先に判定を付けてください」と、その期待結果を示す。
- **最後の区切り**（`final: true`）は、記録を止めたあとにだけ送れる。1 の規則は当てはめない（未判定を含めてよい）。手元に残ったステップが無くても送れる（ステップ 0 件の終了の区切り。`from` は次の番号）。

## 区切りのプレビューと予約

1. パネルは worker に `PREPARE_PART` を送る。worker は書き込みの列の中で区切りの範囲を決め、範囲（`index`・`from`・最後の `seq`）と、区切りのステップを JSON にしたものの要約値（SHA-256）を、記録の中に**予約**として保存して返す。予約は 1 つの記録に同時に 1 つだけで、前の予約は新しい予約で置き換わる。
2. パネルはその範囲で送信データを作り、出口の検査をかけてプレビューする。区切りに NG の期待結果があれば、プレビューに **NG ごとのバグチケットのコピー・保存のボタン**を出す。まだどれも作っていなければ、送信の前に「チケットを作らずに送ると、あとから作れません」と確かめる。
3. 送る直前の照合は、記録全体の版（`revision`）ではなく、**区切りのステップの要約値と予約**で行う（記録中は新しいステップが届き続けるので、記録全体で比べると送れない）。予約が置き換わっていたら送らない。
4. 送信が 2xx で返ったら、パネルは worker に `COMMIT_PART`（記録 ID・`index`・`from`・最後の `seq`・要約値）を送る。
5. worker は書き込みの列の中で、予約と一致するかを確かめ、一致すれば区切りのステップを消し、要約を足し、次の `index`・`from` を進め、予約を消し、`revision` を進める（手で編集した簡易手順の下書きは古いものになる）。
   - 一致しない（別のパネルが別の区切りを予約した、判定が変わった、ステップが消された）ときは何も消さず、パネルに「送った内容と手元が違うので消していない。送信先には届いている」と出す。
   - 送ったステップのうち、上限で先に落ちたものがあっても、残っているものは `seq` で照合して消す（落ちたものは送信先にある）。
6. 送信が失敗したとき・2xx 以外のとき・`COMMIT_PART` の前にパネルが閉じたときは、何も消さない。予約が残っていれば、もう一度送ると同じ `index` になる。受け取る側は同じ記録 ID と `index` を上書きする。
7. 送った期待結果に判定を付けようとすると（`SET_VERDICT`）、worker は `SENT` を返し、パネルは「送信済みのため変更できない」と出す。

## 送信データ（v6）

送信データを v6 に上げ、`recording.part` と `recording.commercialSeen` を足します（ADR 0003 に M6・M7 の行を足してから実装する）。

```json
"recording": {
  "id": "rec-…",
  "part": { "index": 2, "from": 181, "final": false },
  "commercialSeen": true,
  "steps": [ { "n": 181, … }, … ],
  …
}
```

- `part.index`: 区切りの番号。1 から、同じ記録で送った順に増える。
- `part.from`: この区切りの最初の `seq`。`steps[].n` は `from` 以上で、増える順に並ぶ（上限で落ちたりテスターが消したりした番号は飛ぶ）。
- `part.final`: 記録を止めたあとの最後の区切りなら `true`。
- `commercialSeen`: この記録で、商用環境のステップを一度でも記録したか。サイドパネルのメモの環境（ADR 0001。今は残っているステップから決めている）は、区切りを送って商用のステップが手元から消えたあとも、これで決める。
- `part` が無い送信データは、今と同じく記録全体。区切りを 1 つでも送った記録は、残りも区切りとしてだけ送れる。
- そのほかの欄の作り方:
  - `startUrl`・`reproduction`（Markdown・Gherkin）は、その区切りのステップだけから作る。2 つ目以降の区切りでは、始まりの画面を作らない（Gherkin の `Background`「〜を開いている」と、簡易手順の先頭の「〜を開く」を出さない）。代わりに「区切り N の続き（ステップ M から）」と書く。テスターがいたのは前の区切りの最後の画面で、区切りの中の後のステップの URL ではないため。
  - `endedAt`・`notTested` は最後の区切りにだけ入る。`scope`・`targetVersion` はどの区切りにも入る。
  - `privacy.redactions` と `hostsAliased` は記録の始めからの累計。受け取る側は、最後に受け取った区切りの値を使う。
  - 別名（`site-N.invalid`）の対応表は送ったあとも手元に残す。区切りをまたいでも、同じホストは同じ別名になる。
  - `trimmed` は記録全体の印のまま。
  - `webmcpTools` は送る時点の一覧。

### 出口の検査

区切りの送信データにも `checkPayload` と `finalScan` をかけます。`checkPayload` は v6 で次も確かめます。

- `part.index`・`part.from` は 1 以上の整数、`final` は真偽値。
- `steps[].n` は `from` 以上で、増える順（同じ番号が無い）。
- `final` が `false` なら `endedAt`・`notTested` が無い。`final` が `true` なら `endedAt` がある。
- `final` が `false` の区切りに、未判定の期待結果が無い。
- ステップ 0 件は `final` のときだけ。
- サイドパネルのメモの環境が、`commercialSeen` と手元のステップから決まるものと合う。

## 手元に残す要約

送った区切りごとに、次だけを手元に残します（記録の `sent` 欄。送信データには入れない）。

- 区切りの `index`・最初と最後の `seq`・送った日時。
- 期待結果: `ref`・文・判定・実際の結果・画面（ADR 0005 の「期待結果の位置」の伏せた URL）。
- 画面ごとの数: 伏せた URL の移り変わりと、それぞれの「記録された操作・ツール呼び出し・ページからの申告」の数（ADR 0005 の `screenParts`）。区切りの境目で同じ画面が続くときは、次の区切りの最初の画面とまとめる。
- 探索メモ（種類のあるメモ）の文と種類。

要約の形は `shared/payload.js` に送信データと同じ書き方で定義し（ADR 0003 に M8 の行を足す）、書式 A・B に使う前に、送信データと同じく構造の検査をかけます（要約だけ構造の検査を通らずに出口へ出ることがないように）。要約は区切りのステップから worker が作り、文は伏せたあとの runs のまま持ちます。

上限: 期待結果と探索メモは合わせて 500 件、画面は 500 件。要約全体も記録の大きさ（`storeBytes`）に数え、`fitRecord` は手元のステップより先に要約の古いものから消す。要約を消したら `trimmed` を付ける（実施記録の「一部が欠けている」と同じ扱い）。

### 書式 A・B と、ほかの出口

- **実施記録（書式 B）**: 結論・確かめたこと・見つけたこと・画面ごとの数は、要約と手元のステップを合わせて作る。付録（記録したステップ）は手元のステップだけで、その前に「ステップ 1〜M は区切り 1〜N として送信済み」と書く。
- **バグチケット（書式 A）**: NG の期待結果が手元にあるときだけ作れる。再現手順は手元のステップから作り、先頭に「ステップ 1〜M は区切り 1〜N として送信済み。その続きから」と書く。送った区切りの NG は、送る前のプレビューで作る（上の「区切りのプレビューと予約」）。送ったあとはパネルの一覧に出さない。
- **JSON の保存・Markdown・Gherkin・Playwright の下書きのコピー**: 手元に残っているステップだけで作り、送信済みの区切りがあることを書き添える。区切りを送った記録の JSON の保存は、次に送る区切りと同じ形（`part` 付き）にする。

## 中継と Notion

`tools/receiver.mjs` に、Notion へ書く設定を足します。

- 起動の条件: `NOTION_TOKEN` と `NOTION_DATABASE_ID` を渡したときだけ Notion に書く。そのときは、受信の認証（`OPSCRIBE_TOKEN`）と、登録語・実ホスト名の一覧（`OPSCRIBE_KEYWORDS_FILE`）も**必須**にし、無ければ起動しない（中継の `finalScan` は、一覧が無いと登録語と実ホスト名を探せないため。Notion は外部のサービス）。
- 受け取った送信データに今と同じ 2 つの検査をかけ、どちらかで検出があれば 422 を返す。
- 通ったものを `recordings/<記録 ID>/part-<index>.json` に保存し（同じ番号は上書き）、**保存できたら 2xx を返す**。
- Notion には、保存から順に 1 本の列で書く（速さの上限に合わせる）。書けたかどうかは保存の横に記録し、書けていないものは中継の起動時と一定の間隔で書き直す。中継は、Notion に届いていない区切りの一覧を出せる（`GET /status`、127.0.0.1 のみ）。
- DB の 1 行が 1 つの区切り。
  - 固有の列「区切りキー」（`<記録 ID>:<index>`）で行を探し、あれば更新、無ければ作る。行を消して作り直すことはしない（Notion のページは消せず、ゴミ箱と履歴に残るため）。
  - 更新のときは、列を書き換え、本文のブロックを入れ替える。入れ替えで外したブロックも Notion のゴミ箱と履歴に残る（PRIVACY.md に書く）。
  - そのほかの列: 記録 ID・区切りの番号・最初と最後のステップの番号・送信日時・環境（`coverage`）・NG の数・最後の区切りか。
  - 起動時に、DB の data source から列の **property ID と型**を読んで確かめ、合わなければ起動しない（列の名前は人が変えられるため）。`Notion-Version` は中継の中で固定する。
  - 本文: Gherkin と属性表をコードのブロックで入れる。Notion の上限（rich text 1 つは 2000 字、配列は 100 要素、1 回の書き込みは 1000 ブロック・500 KB）に合わせて分けて書く。
  - 429 と 529 は `Retry-After` に従い、ジッターを付けて、回数の上限まで待ち直す。上限を超えたら書けていないものとして残す。

Notion に書くと、検査を通った記録がそのワークスペースに残ります。どの DB に書くか、誰が読めるかは、中継を動かす人が決めて確かめるものです（PRIVACY.md に書く）。

## 既知の限界

- 送った区切りは、あとから消せない。送ったあとに「必ず伏せる語」を足しても、送信先には届いている。送る前のプレビューで確かめる。
- 未判定の期待結果を置いたままだと、そこから先は途中の区切りとして送れない。その間に上限に当たれば、今と同じく古いステップから消える（`trimmed`）。8 割の知らせは、未判定があることも示す。
- 送った NG のバグチケットは、送る前に作らなければ、あとから作れない。
- 区切りの先頭の期待結果は、前の区切りの最後の操作の結果として扱われない。
- 送信が 2xx で返ったあと、`COMMIT_PART` の前にパネルを閉じると、手元に残ったまま送信先にも届いている。もう一度送ると同じ番号の区切りになり、上書きされる。
- 中継が 2xx を返したあと Notion に届くまでには時間がかかる。中継が止まっている間は、保存にだけある。
- 中継が 2xx を返したあとに Notion 側で行が消された、などは拡張から分からない。

## 実装の順

1. ADR 0003 に M6〜M8 を足す。`seq`、送信データ v6（`part`・`commercialSeen`・出口の検査）、`shared/record.js` に区切りの範囲を決める関数・予約・`COMMIT_PART`・要約（上限と `fitRecord`）、`SET_VERDICT` の `SENT`。worker のメッセージ。テストは payload・record・worker。
2. 受信サーバ: v6 を受け付け、区切りを上書きで保存する。サイドパネル: 「ここまでを送る」、区切りのプレビュー（NG のチケットのボタンと確認）、2xx のあとの `COMMIT_PART`、8 割の知らせ。E2E（受信サーバまで）。
3. 書式 A・B を要約と手元のステップから作る。ほかの出口の書き添え。
4. 中継の Notion 書き込み（起動の条件・DB の確認・区切りキーで更新・分けて書く・書き直し・速さの上限・`/status`）と README・PRIVACY・FORMAT。

## 決めなかったこと

- 区切りを、記録を止めずに自動で送ること（プレビューの約束を変えるので、しない）。
- 送った区切りの判定を、あとから更新して送ること（オーナー判断で持たない）。
- 送信先から区切りを取り戻して、手元で書式を作り直すこと。
- 中継が書式 A・B を作ること（書式は拡張の中だけで作る、ADR 0005）。
