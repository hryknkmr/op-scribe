# 0006 記録を区切りごとにファイルへ保存して手元から消す（手元の上限を超えて記録を続ける）

- 状態: 提案
- 日付: 2026-11-05（2026-11-06 に書き直し）
- 関連: ADR 0001（商用環境）、ADR 0003（保証の表）、ADR 0005（書式 A・B、期待結果と判定）

## 背景

記録は `chrome.storage.session`（メモリだけ。ブラウザを閉じると消える）にあり、1 つの記録は 500 ステップ（`LIMITS.steps`）・6 MiB（`LIMITS.storeBytes`）までです。これを超えると古いステップから消えて `trimmed` が付き、長い探索テストでは始めの方の操作が残りません。

上限を上げると、メモリの負担がそのまま増えます。そこで記録の途中で、そこまでのステップを外へ出し、手元から消して記録を続けられるようにします。

## 決めたこと

オーナー判断（2026-11-05）:

- **外へ出す前に必ずプレビューを見る**約束は変えない。自動では出さない。
- きっかけは、手動の「ここまでを保存して手元から消す」と、上限の 8 割（ステップ数か大きさのどちらか）でのパネルの知らせ。知らせはプレビューを自動では開かない。
- 途中の区切りは、**最初の未判定の期待結果の手前まで**。出したあとに判定を付け直す仕組みは持たない。**記録を止めたあとの最後の区切りだけは、未判定を含めてよい**。
- 書式 A・B（バグチケット・実施記録）は、拡張の中だけで作る（ADR 0005 のまま）。そのため:
  - 出した区切りの小さな要約を手元に残し、実施記録は記録全体で作る（2026-11-06 に「台帳だけ残す」に変えた。下）。
  - NG の期待結果を含む区切りは、出す前に、そのバグチケットを作るよう促す。
- Notion の DB は、区切り 1 つを 1 行にし、記録 ID で束ねる（2026-11-08 に見送り。下）。

オーナー判断（2026-11-06。最初の案を 3 回レビューしても収束しなかったため）:

- **拡張は区切りをファイルに保存するだけにする**。外へ通信する新しい出口は作らない。区切りの保存は、今ある「JSON を保存」と同じ出口の検査（`checkPayload` と `finalScan`）を通す。
- **Notion へは、手元の別の CLI が、保存したファイルを読んで書く**（2026-11-08 に見送り。下）。
- 最初の案にあった予約・取り消し・送信の再送・中継の保存は持たない。拡張・中継・Notion の 3 か所で「1 回だけ確実に届けて、手元から消す」を成り立たせようとすると、決める状態が多くなりすぎるためです。

オーナー判断（2026-11-06、書き直した案の 1 回目のレビューのあと）:

- 区切りの保存には `downloads` 権限を足し、`chrome.downloads` でファイルの保存が終わったことを確かめてから手元から消す。テスターの「保存できましたか」の答えでは消さない。インストールのときに「ダウンロードの管理」の警告が増える（README・PRIVACY.md に書く）。
- 区切りを出した記録の実施記録（書式 B）は、ADR 0005 の付録の決まり（ステップを 1 つも省かない）の例外にする。付録は手元のステップだけにし、出した範囲は区切りのファイルにあると書く（ADR 0005 に例外を足す）。

オーナー判断（2026-11-06、2 回目のレビューのあと）:

- 出した区切りの要約（期待結果・通知・画面ごとの数・探索メモ）は手元に持たない。手元に残すのは台帳（数と範囲）だけにする。要約は書式 B の入力を別の形で作り直すもので、書式 B に足すたびに要約にも同じものが要り、2 回続けて欠けが見つかったため。
- 区切りを出した記録の実施記録（書式 B）は、手元に残ったステップだけで作る。結論は台帳の判定の数も合わせて決め、出した区切りの期待結果は区切りのファイルにあると書く。

オーナー判断（2026-11-06、3 回目のレビューのあと）:

- 手元から消す根拠は「Chrome が保存の完了を知らせ、バイト数が合う」こと。`chrome.downloads` の `exists` は古い値を返しうるので使わない。完了のあとにテスターや同期の道具がファイルを消したり移したりするのは、今の「JSON を保存」で保存したファイルを消すのと同じで、拡張の外のこととする。

オーナー判断（2026-11-06、7 回のレビューのあと）:

- この ADR は「区切りをファイルに保存して手元から消す」までの拡張の中だけを扱う。新しく見つかる問題が、拡張の中の状態の組み合わせと、CLI と Notion の制約の 2 つに分かれていて、1 つの ADR で両方を閉じようとしていたため。

オーナー判断（2026-11-08）:

- 区切りのファイルを Notion に書く CLI は、いったん作らない。重要度が低いわりに、決めるべき論点（最後の区切りが無い記録、1 回の書き込みに収まらない区切り、あとで足した登録語）がどれも判断の難しいもので、不要に複雑になるため。区切りのファイルは手元に残るだけで、どこへ持っていくかは使う人が決める。

## ステップの通し番号

ステップを記録に足すとき、worker は手元だけで使う通し番号 `seq` を振ります。番号は 1 から始まり、記録の中で増えるだけです。ステップを消しても振り直しません。区切りのファイルの `steps[].n` は、この `seq` です。

- 次の番号は、記録の欄 `nextSeq` に持つ（`chrome.storage.session` の記録と一緒に保存されるので、worker が止まって起き直しても続く）。
- `chrome.storage.session` は拡張の更新で消えるので、v6 の前に始めた記録は残らない。それでも `nextSeq` を持たない記録があれば、区切りにはしない（残っているステップに後から番号を振らない。どこが消えたかが分からないため）。
- 番号を振るのは、worker が `cleanStep` を通したステップを記録に入れると決めたときだけ。入れなかったステップ（記録を止めた後・許可の無いサイトなど）には振らない。
- 振ったあとに手元から無くなった番号は、理由と一緒に、記録の欄 `removed`（`{ from, to, reason }` の並び）に残す。`reason` は `trimmed`（上限で落ちた）・`deleted`（テスターが消した）・`mixed`（その両方）。
  - 間に手元のステップが無い隣どうしの範囲は、理由が違ってもまとめる（違えば `mixed`）。範囲はいつも手元のステップで隔てられるので、数は手元のステップの数 + 1 を超えない。
  - 区切りを手元から消すとき、`removed` から区切りの範囲（`from`〜`to`）に入る部分を取り除く。`to` をまたぐ範囲は `to` で分け、後ろ（`to + 1` から）を残す（理由は分ける前のまま。`mixed` を分けた後ろが実際には片方の理由だけでも `mixed` のまま）。区切りのファイルの `part.removed` も、同じく `from`〜`to` で切った範囲。

上限で古いステップが落ちても、テスターがステップを消しても、残ったステップの番号は変わりません。出した範囲と手元の照合、区切りの番号は、すべてこの番号で行います。

区切りでない出力（今の記録全体の保存・送信・コピー）の `n` は、今と同じく 1 からの位置です。

## 区切り

区切りは、手元に残っているステップの先頭から、決めた位置までの連続したステップです。終わりの位置は、worker が書き込みの列の中で、次の規則で決めます（待つことはしない）。

1. 途中の区切りは、**最初の未判定の期待結果の手前まで**。期待結果は、テスターがサイドパネルで書いた種類の無いメモ（ADR 0005 の `isExpectation`）です。判定（`verdict`）の無いものが未判定です。ページからの申告（`source: agent`）は判定を持たないので数えません。
2. 途中の区切りは、**手元の最後の操作のまとまりの手前まで**。「どのステップがどの操作の結果か」は、簡易手順（`buildReproduction`）がステップを順に読みながら、直前の操作を覚えて決めています（期待結果と通知は、時間の制限なく直前の操作に付く。遷移は 4 秒（`FOLLOW_MS`）まで）。この読み方を `describe.js` の 1 つの関数に取り出し、簡易手順・Gherkin と区切りの終わりの両方がそれを使います。区切りの終わりは、その関数が返す「操作とその結果のまとまり」の切れ目にだけ置き、最後のまとまりは、いつも次の区切りへ回します。
   - あとから届く期待結果・通知・遷移は、どれも手元の最後の操作に付くので、区切りの中の操作と、区切りの外の結果が分かれることはない（保存のあいだに記録が続いても、区切りの終わりを決め直さずに済む）。
   - 1 の制約で、まとまりの切れ目が区切りの中に無いときは、区切りを出せない（パネルは理由を出す）。
   - ほかの場所で規則を作り直しません。

区切りに入るステップが無いときは、途中の区切りを出せません。先頭が未判定の期待結果なら、パネルは「先に判定を付けてください」と、その期待結果を示します。

**最後の区切り**（`final: true`）は、記録を止めたあとにだけ出せます。1 の規則は当てはめません。最後の区切りは、それまでに振ったすべての番号（`nextSeq - 1` まで）を受け持ちます。手元に残ったステップが無くても出せます（ステップ 0 件の終了の区切り。残りの番号はすべて `removed` で覆う）。最後の区切りを手元から消すと、その記録は閉じます。閉じた記録には、ステップもメモ（`ADD_NOTE`）も区切りも足せません。

## 保存して手元から消す流れ

1. パネルが worker に `PREPARE_PART` を送る。worker は書き込みの列の中で区切りの範囲を決め、次を返します。worker は何も凍結しません。
   - 区切りのステップと、範囲の中の `removed`
   - 範囲（`index`・`from`・`to`）。`index` は、台帳の「最後に消した区切りの番号 + 1」です。
   - 照合の値（`basis`）。区切りのステップごとの `seq` と、そのステップを決まった順の JSON にした SHA-256 の対応表です。手元だけで使い、ファイルには入れません（ファイルに要約値を入れると、`finalScan` が長い 16 進の文字列を ID として止めるため）。
   - 台帳の増分（`delta`）。この区切りのステップから計算した、次の台帳の値（最後の番号・最後の画面・`gaps`・OK・NG・未判定の数）。パネルはプレビューに使うだけで、台帳に入れる値は worker が `PENDING_PART` のときに自分で計算し直して `pending` に持つ（パネルから受け取った値は台帳に入れない）。
2. パネルは区切りのファイルの文を作り、`checkPayload` と `finalScan` をかけてプレビューします。保存するのはこの文そのもの（UTF-8）です。
   - `continuesAt` の URL が今の設定の `finalScan` に当たるとき（区切りを出したあとに登録語を足したときなど）、worker は `continuesAt` を入れず、前提には「前の区切りの最後の画面は書けない（登録語に当たった）」と書く（下の「区切りのファイル」）。
   - 区切りに NG の期待結果があれば、プレビューに NG ごとのバグチケットのコピー・保存のボタンを出し、「チケットを作らずに保存すると、あとから作れません」と書きます（作ったかどうかは拡張から確かめられないので、作ったとは書かない）。
3. テスターが保存を押すと、パネルはまず設定（登録語・別名の一覧）を読み直し、プレビューしたその文に `checkPayload` と `finalScan` をもう一度かけます（今の送信が送る直前に行うのと同じ。プレビューのあとに足した登録語も効かせるため）。検出があれば保存しません。
4. 通れば、保存を始める**前に**、パネルは worker に `PENDING_PART` を送ります。中身は、記録 ID・`index`・`from`・`to`・`basis`・ファイル名・バイト数・Blob の URL です。
   - worker は書き込みの列の中で、`index` が台帳の次の番号であること、範囲の中に今あるステップが `basis` とちょうど同じ（同じ番号の集まりで、どれも値が同じ）であることを確かめる。プレビューのあとに範囲のステップが 1 つでも無くなっていたり変わっていたりすれば、理由（テスターが消した・判定を変えた・上限で落ちた）を問わず断る（理由を見分けなくて済むように、安全な側に倒す）。合わなければ断り、パネルは「プレビューが古くなりました。もう一度プレビューしてください」と出す（別のパネルの古いプレビューで、保存済みの同じ番号のファイルを上書きしないため。ダウンロードを始める前に断る）。
   - 合えば、worker は `basis` のステップから台帳の増分（`delta`）を計算して、`pending` に残し、使い捨ての印（`nonce`）を付けて返す。`pending` は 1 つの記録に 1 つだけ。
   - **`pending` のあいだ、区切りの範囲（`from`〜`to`）のステップは上限でも落とさない**（`fitRecord` はそれ以外から落とす。範囲のほかに落とせるものが無ければ、新しく届いたステップを記録せず `trimmed` を付ける）。保存が失敗しても、やめても、区切りのステップは手元に残る。保存は数秒で終わるので、範囲を固定するのもこの間だけ。
   - **`pending` のあいだ、テスターによる記録の変更は、`STOP` を除いてすべて断る**: `PREPARE_PART`・`DELETE_STEP`・`SET_VERDICT`・`ADD_NOTE`・`CLEAR`・`START`（新しい記録）・記録の欄の書き換え。パネルは「保存中です。終わるか、保存をやめてから」と出す。保存は数秒で終わるので、この間だけ待たせる（保存のあいだの変更と、ファイルに出た中身の食い違いを、起きたあとに見つけるのでなく、起きないようにするため）。
   - ページから届くステップ（`STEP`・`WEBMCP_*`）と、記録を止める `STOP` は今までどおり受け付ける。届いたステップと、`STOP` が書く `state`・`endedAt`・`notTested` と、止めるときに流し込むステップは、どれも区切りの後ろ（`to` より後）と記録の欄に入るので、保存中の区切りの中身は変わらない。途中の区切りのファイルは `endedAt: null` のままで、止めたことは最後の区切りに入る。
5. パネルは `chrome.downloads.download` で、その文を `<記録 ID>.part-<index>.opscribe.json` としてダウンロードのフォルダに保存します（`saveAs: false`、同じ名前があれば上書き）。返ったダウンロードの ID は、印と一緒に worker に送ります（`PENDING_DOWNLOAD`）。
   - パネルは保存に使う Blob の URL を `PENDING_PART` に入れておく（Blob の URL は作るたびに違う）。worker は印が合い、`chrome.downloads.search` で読んだそのダウンロードが、この拡張のもの（`byExtensionId`）で、`url` が `pending` の Blob の URL と同じときだけ、ID を `pending` に足す。足した直後にそのダウンロードの状態を読む（ID が届く前に保存が終わっていても、取りこぼさないため）。合わない `PENDING_DOWNLOAD` は断る。
   - パネルは、worker が `PENDING_DOWNLOAD` を受け取ったと返すまで「保存しました」と出さない。保存に使う Blob の URL は、ダウンロードが終わるまで破棄しない（今の「JSON を保存」は 1 秒で破棄するが、大きい区切りでは途中で止まるため）。
   - ID の無い `pending` は、worker が起き直したとき・パネルを開いたときに、`chrome.downloads.search({ url })` で、`url` が `pending` の Blob の URL と同じで、この拡張の（`byExtensionId`）ダウンロードを探す。ちょうど 1 つのときだけそれに決める。0 件なら外さず「保存の開始待ち」のまま残し（パネルがまだ保存を始めていないだけかもしれないため）、2 件以上なら手元からは消さずに `pending` を外して「保存できませんでした」と出す。ファイル名と時刻では決めない（ほかの拡張がファイル名を変えることがあり、時刻では 1 つに決まらないため）。
   - 「保存の開始待ち」は、合う `PENDING_DOWNLOAD` が届くか、テスターがパネルで「保存をやめる」を選んだときだけ終わる。やめたあとに届いた `PENDING_DOWNLOAD` と、そのダウンロードの完了は無視する（手元からは消さない。同じ名前のファイルは次の保存で上書きされる）。
6. worker は `chrome.downloads.onChanged` で、そのダウンロードの終わりを待ちます。worker が止まって起き直したときと、パネルを開いたときは、`chrome.downloads.search` でそのダウンロードの今の状態を読み直します（止まっていたあいだの知らせを取りこぼさないため）。
   - 状態が `complete` で、受け取ったバイト数（`bytesReceived`・`totalBytes`）が送ったバイト数と同じなら、worker は書き込みの列の中で手元から消す（`COMMIT_PART`）。ファイルは拡張が作った Blob の URL から保存するので、大きさは分かっている。`exists` は使わない（Chrome はファイルを見張っておらず、古い値を返すことがあるため）。
   - 手元から消す前に、次を確かめる。
     - `index` が台帳の次の番号であること。
     - 範囲の中に今あるステップが `basis` とちょうど同じであること（`PENDING_PART` のときに確かめ、そのあとはテスターの変更を断り、上限でも落とさないので、合わないのは実装の誤り）。
     - 最後の区切りなら、記録が止まっていて、`to` が `nextSeq - 1` であること。
   - すべて合えば、範囲のステップと範囲の `removed` を消し、台帳に `pending` の `delta`（worker が計算したもの）を入れ、`pending` を外し、`revision` を進めます（手で編集した簡易手順の下書きは古いものになる）。
7. 確かめが合わなければ、消さずに `pending` を外し、「保存できたファイルと手元が合いません。手元は消していません」と出します（起きないはずの場合。保存したファイルはそのまま残るので、テスターが確かめる）。
8. 次のときも、消さずに `pending` を外し、「保存できませんでした」と理由を出します。
   - ダウンロードが `interrupted` になったとき
   - `complete` でも、バイト数が分からない（`-1`）か合わないとき
   - ダウンロードが見つからないとき（テスターが一覧から消した、など）

区切りを 1 つでも手元から消した記録は、残りも区切りとしてだけ出せます。その記録の送信（`POST`）はできなくします（今の受信サーバは記録 ID ごとに 1 つのファイルに上書きするので、区切りを送ると前のものが消えるため）。コピーは、手元に残ったステップだけで作り、出した区切りがあることを書き添えます（下の「ほかの出口」）。

## 区切りのファイル（送信データ v6）

区切りのファイルは送信データと同じ形で、v6 に上げて `recording.part`・`recording.commercialSeen`・`recording.earlier` を足します（ADR 0003 に M6〜M8 の行を足してから実装する）。

```json
"recording": {
  "id": "rec-…",
  "part": { "index": 2, "from": 181, "to": 342, "removed": [{ "from": 181, "to": 185, "reason": "trimmed" }],
            "final": false, "continuesAt": { "url": "https://site-1.invalid/list", "env": "standard" } },
  "commercialSeen": true,
  "earlier": { "parts": 1, "through": 180, "ok": 4, "ng": 0, "open": 0, "gaps": false },
  "steps": [ { "n": 181, … }, … ],
  …
}
```

- `part.index`: 区切りの番号。1 から、同じ記録で手元から消した順に増える。
- `part.from`・`part.to`: この区切りが受け持つ番号の範囲。`from` は台帳の「最後に消した `seq` + 1」（区切り 1 は 1）で、`to` は範囲の最後の番号。最後の区切りでは `nextSeq - 1`（番号を 1 つも振っていなければ `from - 1`）。
- `part.removed`: 範囲の中で手元から無くなった番号と理由（記録の `removed` のうち範囲に入るもの）。`steps[].n` と `removed` を合わせると、`from` から `to` までの番号がちょうど 1 回ずつ現れる。
- `part.final`: 最後の区切りなら `true`。
- `part.continuesAt`: 2 つ目以降の区切りで、それより前の区切りの最後の画面（前の区切りのうち、URL を持つ最後のステップ。前の区切りに URL を持つステップが無ければ、前の区切りの `continuesAt`）。`{ url, env }` の形で、`url` はそのステップの `url`、`env` はそのステップの `env`（`commercial`・`standard`）。台帳から取ります。`checkPayload` は `url` を、この `env` でステップの `url` と同じ規則で確かめます（商用なら商用の規則）。どの区切りにも URL を持つステップが無いとき、その URL が今の設定の `finalScan` に当たるときは、ありません。当たったときは `part.continuesHidden: true` を入れ、前提に「前の区切りの最後の画面は書けない（登録語に当たった）」と書きます。
- `commercialSeen`: この記録で、商用環境のステップを一度でも記録したか。サイドパネルのメモの環境（ADR 0001）は、`describe.js` の 1 つの関数が「`commercialSeen` か、残っているステップに商用がある」で決めます。worker のメモの伏せ方（`cleanStep`）・`buildPayload`・`checkPayload`・WebMCP の応答に付ける Gherkin（`webmcpReply` の `envSteps`）は、どれもこの関数を使います（今は残っているステップだけで決めているので、商用のステップを出して消すと、そのあとのメモが緩く伏せられる）。
- `part.continuesHidden`: 上の、前の画面の URL を検査で入れられなかったときだけ `true`。
- そのほかの欄の作り方。v6 の区切りでは、次の規則が今の規則に置き換わる（`buildPayload` は区切りを受け取って作り、`checkPayload` と `toGherkin` は `part` があるときこの規則で確かめる・作り直す）:
  - `steps[].n` は `seq`（今の「1 からの位置」の検査は、区切りでは上の `from`・`to`・`removed` の検査に置き換わる）。
  - `startUrl`: 区切り 1 は今と同じ（ステップの最初の URL）。2 つ目以降は `part.continuesAt`、それが無ければ `[[url:none]]`。今の「ステップの最初の URL であること」の検査は、区切り 2 以降では「`continuesAt` と同じであること」に置き換わる。
  - 区切りに `part.removed` があり、その中に区切りの最初の URL を持つステップより前の番号があるとき（区切り 1 でも）、Markdown と Gherkin の前提に「この画面の前に、記録から消えた操作がある（消した・上限で落ちた）。この画面は、それを含めた操作のあとの状態」と書く。`toGherkin` はこれを `part` から決め、`checkPayload` は同じ規則で作り直して比べる。
  - `reproduction`（Markdown・Gherkin）は、その区切りのステップと `part` から作る。Markdown はいつもテンプレートで作り（`generator: template`）、サイドパネルで手で編集した簡易手順の下書きは区切りのファイルに入れない（下書きは記録全体に対して書いたもので、区切りの範囲と合わないため。下書きは手元に残り、区切りを手元から消すと古いものになる）。2 つ目以降の区切りは、前提（Gherkin の `Background`）に「区切り N の続き。前の区切りの操作をすべて終えた状態で、この画面から」と書き（`earlier.gaps` が `true` なら「前の区切りには記録から消えた操作がある（消した・上限で落ちた）」も書く）、画面は `continuesAt`。`continuesAt` が無ければ「前の区切りの最後の画面は記録に無い」（`continuesHidden` なら「書けない（登録語に当たった）」）と書く。`checkPayload` の「Gherkin が記録から作り直したものと同じ」の検査は、この規則の `toGherkin` で行う。
  - `endedAt` は、最後の区切りでだけ値を持ち、途中の区切りでは `null`。`notTested` は最後の区切りにだけ入る。`scope` と `targetVersion` は、どの区切りにも同じ値で入る。
  - `privacy.redactions` と `hostsAliased` は、記録の始めからの累計。
  - 別名（`site-N.invalid`）の対応表は、区切りを出したあとも手元に残す。区切りをまたいでも、同じホストは同じ別名になる。
  - `trimmed` は記録全体の印のまま。`webmcpTools` はファイルを作る時点の一覧。

### 出口の検査

区切りのファイルにも、今の保存と同じく `checkPayload` と `finalScan` をかけます。`checkPayload` は、v6 では次も確かめます。

- `part.index`・`part.from` は 1 以上の整数、`to` は `from - 1` 以上の整数、`final` は真偽値、`continuesAt` は URL の形（`index` が 1 なら `continuesAt` が無く、`from` は 1）。
- `steps[].n` は増える順（同じ番号が無い）。`steps[].n` と `removed` の範囲を合わせると、`from` から `to` までがちょうど 1 回ずつ現れる。`removed` の `reason` は `trimmed`・`deleted`・`mixed` のどれかで、隣どうしの範囲は続かない（間に `steps[].n` がある）。
- `final` が `false` なら `endedAt` が `null` で `notTested` が無く、未判定の期待結果も無い。`final` が `true` なら `endedAt` がある。
- `earlier` は `parts`・`through`・`ok`・`ng`・`open`（0 以上の整数）と `gaps`（真偽値）だけ。`open` は最後の区切りのあとにだけ 0 より大きくなりうる（途中の区切りは未判定を含まないため）。区切りのファイルでは、`index` が 1 なら無く、2 以上なら `parts` が `index - 1`、`through` が `from - 1`。
- ステップ 0 件は `final` のときだけ。（`final` の `to` が記録の最後の番号であることは、1 つのファイルからは確かめられないので、worker が手元から消すときに確かめる。上の流れの 6。）
- サイドパネルのメモの環境が、`commercialSeen` と手元のステップから決まるものと合う。
- `steps` に商用のステップが 1 つでもあれば、`commercialSeen` が `true`（worker は商用のステップを記録に入れるのと同じ処理で `commercialSeen` を立てる。過去の区切りの分は 1 つのファイルからは確かめられないが、見えている食い違いは止める）。

## 手元に残すもの（台帳）

手元から区切りを消すとき、worker は記録の台帳（`ledger`）を進めます。台帳は小さく、上限でも消しません。台帳・`removed`・`pending` も記録の大きさ（`storeBytes`）に数え、`fitRecord` はそれを入れて上限を計算します（ステップを落とすと `removed` が増えるので、落としたあとの大きさで確かめ直す）。

- 最後に消した区切りの番号
- 最後に消した `seq`（区切りの `to`）
- 前の区切りの最後の画面（`continuesAt` の元。ステップの `url` と同じ伏せ方の URL と、そのステップの `env`）
- 前の区切りのどれかに `removed` があったか（`gaps`）
- 出した区切りの判定の数の累計（OK・NG・未判定。未判定は最後の区切りにだけありうる。閉じた記録の実施記録の結論に要る）
- 閉じたか

出した区切りの期待結果・通知・画面・探索メモは、手元には残しません（区切りのファイルにある）。

台帳のうち出口が使うものは、送信データ v6 の `recording.earlier` に入れます。

```json
"earlier": { "parts": 3, "through": 342, "ok": 12, "ng": 1, "open": 0, "gaps": true }
```

- `parts`: 手元から消した区切りの数。`through`: 最後に消した `seq`。`ok`・`ng`・`open`: その区切りの期待結果の OK・NG・未判定の数（0 以上の整数）。`gaps`: その区切りのどれかに `removed` があったか（真偽値）。
- 区切りを 1 つも消していない記録には無い。区切りのファイルでは、そのファイルより前の区切りの累計（区切り 1 には無い）。
- 書式 A・B は、ほかの欄と同じく `buildPayload` の結果（`checkPayload` を通したもの）だけから作るので、台帳の数もその検査を通ってから書式に入る。台帳の文字（前の画面の URL）は `part.continuesAt` として区切りのファイルにだけ入り、ステップの URL と同じ検査を通る。

### ほかの出口

- **実施記録（書式 B）**:
  - 結論は、ADR 0005 の「結論の決め方」の表をそのまま使い、表の OK・NG・未判定の件数を「`earlier` の `ok`・`ng`・`open` + 手元の期待結果の OK・NG・未判定」、`trimmed` を記録の `trimmed` にして当てはめる（最後の区切りを出して閉じた記録では、手元のステップは無く、結論は `earlier` だけで決まる）。期待結果の件数は、この OK・NG・未判定の合計。
  - 冒頭に「ステップの番号 1〜{through} は区切り 1〜{parts} として保存済み（遷移・通知・メモも含む全ステップの番号で、消したもの・上限で落ちたものの番号も含む範囲）。保存したときに残っていた期待結果（OK n 件・NG m 件・未判定 k 件）は区切りのファイルにある」と書く（保存の前に上限で落ちた期待結果は、どのファイルにも無い）。
  - 確かめたこと・見つけたこと・画面ごとの数・付録は、手元に残ったステップだけで作る（ADR 0005 の例外）。
- **バグチケット（書式 A）**: NG の期待結果が手元にあるときだけ作れる。再現手順は手元のステップから作り、先頭に「ステップの番号 1〜{through} は区切り 1〜{parts} として保存済み（全ステップの番号で、消したものの番号も含む範囲）。その続きから」と書く。始まりの画面は、手元の最初の URL ではなく、台帳の前の画面にする（区切りのファイルの `startUrl` と同じ規則）。
- **区切りのプレビューで作るバグチケット**: 区切りの中の NG のチケットは、その区切りのファイル（`part`・`earlier` 付き）から作る。2 つ目以降の区切りでは、再現手順の先頭に、区切りのファイルの前提と同じ文（「区切り N の続き…」と、欠けた操作があればその文）を書き、始まりの画面を `continuesAt` にする。`bugTickets` と `sessionRecord` は `part` と `earlier` を読んで作る。
- **JSON の保存・Markdown・Gherkin・Playwright の下書きのコピー**: 手元に残っているステップだけで作り、保存済みの区切りがあることを書き添える。区切りを出した記録の「JSON を保存」は、「ここまでを保存して手元から消す」と同じ区切りの保存に置き換える。
- **送信（`POST`）**: 区切りを出した記録ではできない（上の「保存して手元から消す流れ」）。

## 区切りのファイルを読む側

区切りのファイルを読んで外へ書く道具は作りません（上の 2026-11-08 の判断）。拡張がファイルについて約束するのは、上の「区切りのファイル」と「出口の検査」だけです。受信サーバ（`tools/receiver.mjs`）は、`recording.part` か `recording.earlier` を持つ送信データを 422 で断ります（区切りを出した記録はファイルでだけ出す。今の受信サーバは記録 ID ごとに上書きするので、残りだけの送信データで前のものが消えるため）。

## 既知の限界

- 保存した区切りは、拡張から取り消せない。保存したあとに「必ず伏せる語」を足しても、ファイルには残っている。保存の前のプレビューで確かめる。
- 未判定の期待結果を置いたままだと、そこから先は途中の区切りとして出せない。その間に上限に当たれば、今と同じく古いステップから消える（`trimmed`）。8 割の知らせは、未判定があることも示す。
- 手元の最後の操作のまとまりは、途中の区切りに入らない。区切りを出したあとも、手元にはいつも少しステップが残る。
- 区切りに入った NG のバグチケットは、保存の前に作らなければ、あとから作れない。
- 区切りを出した記録の実施記録は、手元に残ったステップの分だけ。出した区切りの期待結果・画面・探索メモは、数のほかは書かれない（区切りのファイルを見る）。
- 拡張が確かめるのは、Chrome が保存の完了を知らせ、バイト数が合うことまで。完了の直後でも、テスターや同期の道具がファイルを消したり移したりしたことは分からず、手元からは消える（オーナー判断で受け入れた限界）。
- 保存のあいだ（保存を押してから終わるまで）は、テスターは記録を変えられない（消す・判定・メモ・クリア・新しい記録）。プレビューのあとに変えると、保存のときに断られ、プレビューからやり直す。
- 区切りの先頭の期待結果は、前の区切りの最後の操作の結果として扱われない（最後のまとまりを次へ回すので、起きるのは区切りの先頭が期待結果だけのときに限られる）。
- 記録は今と同じく `chrome.storage.session` にあるので、ブラウザの再起動・拡張の更新で、手元のステップと台帳が消える。保存した区切りのファイルは残るが、最後の区切りは作れない。
- 記録の始めに書いた欄（`scope`・`targetVersion`）が、あとで足した登録語に当たると、その記録の残りはどの出口からも出せない（今の記録と同じ）。

## 決めなかったこと

- 区切りを、自動で出すこと（プレビューの約束を変えるので、しない）。
- 出した区切りの判定を、あとから付け直すこと（オーナー判断で持たない）。
- 拡張から Notion や中継へ、区切りを直接送ること（2026-11-06 の判断で持たない）。
- 区切りのファイルを Notion などへ書く道具（2026-11-08 の判断で、いったん作らない）。
