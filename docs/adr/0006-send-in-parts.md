# 0006 記録を区切りごとにファイルへ出して手元から消す（手元の上限を超えて記録を続ける）

- 状態: 提案
- 日付: 2026-11-05（2026-11-06 に書き直し）
- 関連: ADR 0001（商用環境）、ADR 0003（保証の表）、ADR 0005（書式 A・B、期待結果と判定）

## 背景

記録は `chrome.storage.session`（メモリだけ。ブラウザを閉じると消える）にあり、1 つの記録は 500 ステップ（`LIMITS.steps`）・6 MiB（`LIMITS.storeBytes`）までです。これを超えると古いステップから消えて `trimmed` が付き、長い探索テストでは始めの方の操作が残りません。

上限を上げると、メモリの負担がそのまま増えます。そこで記録の途中で、そこまでのステップを外へ出し、手元から消して記録を続けられるようにします。

## 決めたこと

オーナー判断（2026-11-05）:

- **外へ出す前に必ずプレビューを見る**約束は変えない。自動では出さない。
- きっかけは、手動の「ここまでを保存して手元から消す」と、上限の 8 割（ステップ数か大きさのどちらか）でのパネルの知らせ。知らせはプレビューを自動では開かない。
- 途中の区切りは、**最初の未判定の期待結果の手前まで**。出したあとに判定を付け直す仕組みは持たない。**記録を止めたあとの最後の区切りだけは、未判定を含めてよい**。
- 書式 A・B（バグチケット・実施記録）は、拡張の中だけで作る（ADR 0005 のまま）。そのため:
  - 出した区切りの小さな要約を手元に残し、実施記録は記録全体で作る。
  - NG の期待結果を含む区切りは、出す前に、そのバグチケットを作るよう促す。
- Notion の DB は、区切り 1 つを 1 行にし、記録 ID で束ねる。

オーナー判断（2026-11-06。最初の案を 3 回レビューしても収束しなかったため）:

- **拡張は区切りをファイルに保存するだけにする**。外へ通信する新しい出口は作らない。区切りの保存は、今ある「JSON を保存」と同じ出口の検査を通す。
- **Notion へは、手元の別の CLI（`tools/notion-sync.mjs`）が、保存したファイルを読んで書く**。拡張と CLI は、ファイルでだけつながる。
- 最初の案にあった予約・取り消し・送信の再送・中継の保存は持たない。拡張・中継・Notion の 3 か所で「1 回だけ確実に届けて、手元から消す」を成り立たせようとすると、決める状態が多くなりすぎるためです。

## ステップの通し番号

ステップを記録に足すとき、worker は手元だけで使う通し番号 `seq` を振ります。番号は 1 から始まり、記録の中で増えるだけです。ステップを消しても振り直しません。区切りのファイルの `steps[].n` は、この `seq` です。

上限で古いステップが落ちても、テスターがステップを消しても、残ったステップの番号は変わりません。出した範囲と手元の照合、区切りの番号は、すべてこの番号で行います。

区切りでない出力（今の記録全体の保存・送信・コピー）の `n` は、今と同じく 1 からの位置です。

## 区切り

区切りは、手元に残っているステップの先頭から、決めた位置までの連続したステップです。終わりの位置は、worker が書き込みの列の中で、次の規則で決めます（待つことはしない）。

1. 途中の区切りは、**最初の未判定の期待結果の手前まで**。期待結果は、テスターがサイドパネルで書いた種類の無いメモ（ADR 0005 の `isExpectation`）です。判定（`verdict`）の無いものが未判定です。ページからの申告（`source: agent`）は判定を持たないので数えません。
2. 区切りの終わりは、操作とその結果を分けない位置に寄せる。操作の直後の遷移・通知がその操作の結果にあたるなら、それも区切りに入れます。まだ 4 秒（`FOLLOW_MS`）たっていない最後の操作は、それに続くものと一緒に次の区切りへ回します。
   - 区切りの終わりを決める関数は `describe.js` に置き、簡易手順・Gherkin が操作と遷移・通知を結びつけるのと同じ規則（`followsOperation`）を使います。ほかの場所で規則を作り直しません。
   - 1 の制約でこの規則を守れないときは、その操作の手前まで寄せます。

区切りに入るステップが無いときは、途中の区切りを出せません。先頭が未判定の期待結果なら、パネルは「先に判定を付けてください」と、その期待結果を示します。

**最後の区切り**（`final: true`）は、記録を止めたあとにだけ出せます。1 の規則は当てはめません。手元に残ったステップが無くても出せます（ステップ 0 件の終了の区切り）。最後の区切りを手元から消すと、その記録は閉じます。閉じた記録には、ステップも区切りも足せません。

## 保存して手元から消す流れ

1. パネルが worker に `PREPARE_PART` を送る。worker は書き込みの列の中で区切りの範囲を決め、次を返します。
   - 区切りのステップ
   - 範囲（`index`・`from`・`to`）
   - 照合の値（`basis`）。区切りのステップを決まった順の JSON にした SHA-256 で、手元だけで使い、ファイルには入れません。

   `index` は、手元の台帳の「最後に消した区切りの番号 + 1」です。worker は何も凍結しません。
2. パネルは区切りのファイルを作り、`checkPayload` と `finalScan` をかけてプレビューします。区切りに NG の期待結果があれば、プレビューに NG ごとのバグチケットのコピー・保存のボタンを出し、「チケットを作らずに保存すると、あとから作れません」と書きます（作ったかどうかは拡張から確かめられないので、作ったとは書かない）。
3. テスターが保存すると、ファイル `<記録 ID>.part-<index>.opscribe.json` を保存します。保存の仕方は、今の「JSON を保存」と同じです。
4. パネルは「ファイルを保存できましたか。手元から消します」と確かめます。
   - 「はい」なら、パネルは worker に `COMMIT_PART`（記録 ID・`index`・`from`・`to`・`basis`）を送る。
   - worker は書き込みの列の中で、次を確かめる。
     - `index` が台帳の次の番号であること
     - 範囲の中に今あるステップから計算した値が `basis` と同じであること
     - 最後の区切りなら、記録が止まっていること
   - すべて合えば、範囲のステップを消し、要約と台帳を進め、`revision` を進めます（手で編集した簡易手順の下書きは古いものになる）。
5. 合わなければ消さずに、「保存したあとに、この範囲のステップが変わりました。保存したファイルを消してから、もう一度保存してください」と出します。
   - 合わないのは、保存のあいだにテスターが範囲のステップを消した・判定を変えた、または上限で範囲のステップが落ちたときです。
   - 古いファイルを消し忘れても、CLI が同じ番号の食い違うファイルとして止めます（下の「CLI」）。
6. 「いいえ」なら何も変えません。

区切りを 1 つでも手元から消した記録は、残りも区切りとしてだけ出せます。送信（`POST`）とコピーは、手元に残ったステップだけで作り、出した区切りがあることを書き添えます（下の「ほかの出口」）。

## 区切りのファイル（送信データ v6）

区切りのファイルは送信データと同じ形で、v6 に上げて `recording.part` と `recording.commercialSeen` を足します（ADR 0003 に M6・M7 の行を足してから実装する）。

```json
"recording": {
  "id": "rec-…",
  "part": { "index": 2, "from": 181, "final": false, "continuesAt": "https://site-1.invalid/list" },
  "commercialSeen": true,
  "steps": [ { "n": 181, … }, … ],
  …
}
```

- `part.index`: 区切りの番号。1 から、同じ記録で手元から消した順に増える。
- `part.from`: この区切りの最初の `seq`。台帳の「最後に消した `seq` + 1」。`steps[].n` は `from` 以上で、増える順に並ぶ（落ちたり消したりした番号は飛ぶ）。
- `part.final`: 最後の区切りなら `true`。
- `part.continuesAt`: 2 つ目以降の区切りで、前の区切りの最後の画面。台帳から取り、ステップの `url` と同じ伏せ方の URL です。前の区切りに URL を持つステップが無ければ、ありません。
- `commercialSeen`: この記録で、商用環境のステップを一度でも記録したか。サイドパネルのメモの環境（ADR 0001）は、`describe.js` の 1 つの関数が「`commercialSeen` か、残っているステップに商用がある」で決めます。worker のメモの伏せ方（`cleanStep`）・`buildPayload`・`checkPayload` は、どれもこの関数を使います（今は残っているステップだけで決めているので、商用のステップを出して消すと、そのあとのメモが緩く伏せられる）。
- そのほかの欄の作り方:
  - `startUrl` と `reproduction`（Markdown・Gherkin）は、その区切りのステップだけから作る。2 つ目以降の区切りの始まりの画面は `part.continuesAt` にし、「区切り N の続き。前の区切りの操作をすべて終えた状態で、この画面から」と書く。`continuesAt` が無ければ、「前の区切りの最後の画面は記録に無い」と書く。
  - `endedAt` と `notTested` は、最後の区切りにだけ入る。`scope` と `targetVersion` は、どの区切りにも入る。
  - `privacy.redactions` と `hostsAliased` は、記録の始めからの累計。
  - 別名（`site-N.invalid`）の対応表は、区切りを出したあとも手元に残す。区切りをまたいでも、同じホストは同じ別名になる。
  - `trimmed` は記録全体の印のまま。`webmcpTools` はファイルを作る時点の一覧。

### 出口の検査

区切りのファイルにも、今の保存と同じく `checkPayload` と `finalScan` をかけます。`checkPayload` は、v6 では次も確かめます。

- `part.index`・`part.from` は 1 以上の整数、`final` は真偽値、`continuesAt` は URL の形（`index` が 1 なら無い）。
- `steps[].n` は `from` 以上で、増える順（同じ番号が無い）。
- `final` が `false` なら `endedAt`・`notTested` が無く、未判定の期待結果も無い。`final` が `true` なら `endedAt` がある。
- ステップ 0 件は `final` のときだけ。
- サイドパネルのメモの環境が、`commercialSeen` と手元のステップから決まるものと合う。

## 手元に残すもの

手元から区切りを消すとき、worker は記録に 2 つを残します（送信データには入れない）。

**台帳**（`ledger`。消さない・小さい）:

- 最後に消した区切りの番号
- 最後に消した `seq`
- 前の区切りの最後の画面（`continuesAt` の元）
- 判定の数の累計（`sentTotals`。OK・NG・未判定）
- 閉じたか

**要約**（`sent`。上限で古いものから消す）:

- 区切りごとの番号・範囲・日時
- 期待結果: `ref`・文・判定・実際の結果・画面
- 画面ごとの数（ADR 0005 の `screenParts`）
- 探索メモの文と種類

要約は区切りのステップから worker が作り、文は伏せたあとの runs のまま持ちます。

台帳と要約の形は、`shared/payload.js` に送信データと同じ書き方で定義します（ADR 0003 に M8 の行を足す）。書式 A・B に使う前に、構造の検査（`checkSent`）と `finalScan` をかけます。

要約の上限:

- 期待結果と探索メモは合わせて 500 件、画面は 500 件まで。
- 要約も記録の大きさ（`storeBytes`）に数える。`fitRecord` は、手元のステップより先に要約の古い詳細から消し、消したら `trimmed` を付ける。
- 台帳は消さないので、区切りの番号・`from`・`continuesAt` と、実施記録の結論（NG があれば「問題あり」）は、詳細が欠けても正しく決まる。
- 詳細が欠けているときは、NG が 0 件でも「確かめた範囲で問題なし」とは書かず、「判定の詳細の一部が欠けている（OK n 件・NG 0 件・未判定 m 件）」と書く。

出した期待結果に判定を付けようとすると（`SET_VERDICT`）、worker は `SENT` を返し、パネルは「出したあとのため変更できない」と出します。

### ほかの出口

- **実施記録（書式 B）**:
  - 結論は、台帳の `sentTotals` と手元のステップから決める。
  - 確かめたこと・見つけたこと・画面ごとの数は、要約と手元のステップを合わせて作る。
  - 付録は手元のステップだけで、その前に「ステップ 1〜M は区切り 1〜N として保存済み」と書く。
- **バグチケット（書式 A）**: NG の期待結果が手元にあるときだけ作れる。再現手順は手元のステップから作り、先頭に「ステップ 1〜M は区切り 1〜N として保存済み。その続きから」と書く。区切りに入った NG のチケットは、保存の前のプレビューで作る。
- **JSON の保存・送信・Markdown・Gherkin・Playwright の下書きのコピー**: 手元に残っているステップだけで作り、保存済みの区切りがあることを書き添える。区切りを出した記録の JSON の保存は、次の区切りと同じ形（`part` 付き）にする。

## CLI（`tools/notion-sync.mjs`）

保存した区切りのファイルを読み、Notion の DB に書く手元の CLI です。拡張とは別に、テスターが手で動かします。

```sh
node tools/notion-sync.mjs <ファイルのあるフォルダ> [--dry-run]
```

**起動の条件**:

- 環境変数 `NOTION_TOKEN`・`NOTION_DATA_SOURCE_ID`・`OPSCRIBE_KEYWORDS_FILE`（登録語・実ホスト名の一覧）がすべて要る。一覧が無いと、`finalScan` が登録語と実ホスト名を探せないため。
- 同じフォルダで 2 つ同時に動かさない。フォルダに `.notion-sync.lock` を排他で作り（作れなければ止まる）、終わったら消す。
- 起動時に、DB の data source から列の property ID と型を読んで確かめ、合わなければ止まる（列の名前は人が変えられるため）。`Notion-Version` は CLI の中で固定する。

**ファイルの検査**: `*.part-*.opscribe.json` を読み、それぞれに `checkPayload` と `finalScan` をかけます。検出があったファイルは書かずに知らせます。

**書く記録の選び方**（ファイルの中身だけで決める）:

- 記録 ID ごとに区切りを集め、最後の区切り（`final: true`）があり、番号が 1 から欠けずに続く記録だけを書く。
- 前の区切りの最後の `n` より、次の区切りの `from` が大きいことも確かめる。
- 同じ記録 ID と番号で中身（ファイルのバイト列の SHA-256）が違うファイルが 2 つ以上あれば、その記録は書かずに、ファイル名を挙げて知らせる。人がどちらかを消してから動かし直す。
- 記録の途中の区切りを先に書くことはしない（書いたあとに同じ番号の別の中身が保存されると、食い違いが Notion に残るため）。

**Notion への書き方**:

- 1 つの区切りを 1 行にする。
  - 列「区切りキー」（`<記録 ID>:<index>`）と、列「中身の要約値」（ファイルの SHA-256）を持つ。
  - そのほかの列は、記録 ID・区切りの番号・最初と最後のステップの番号・環境（`coverage`）・NG の数・最後の区切りか。
- 書く前に、区切りキーで DB を探す。
  - 無ければ、列と本文のブロックを **1 回の書き込みで**作る。
  - 1 行あって要約値が同じなら、書き済みとして飛ばす。
  - 1 行あって要約値が違うとき、2 行以上あるときは、書かずに知らせる。
  - 行を更新したり、消して作り直したりはしない（Notion のページは消せず、ゴミ箱と履歴に残るため）。
- 本文は、Gherkin と属性表をコードのブロックで入れる。Notion の上限（rich text 1 つは 2000 字、配列は 100 要素、1 回の書き込みは 1000 ブロック・500 KB）に合わせて分ける。1 回の書き込みに収まらない区切りは、書かずに知らせる。
- **Notion は新しい出口**なので、実際に書く列の値と本文のブロックの文字すべてに、書く直前に `finalScan` をかける。検出があれば書かない。
- 書き込みは 1 本ずつ順に行う。429 と 529 は `Retry-After` に従い、ジッターを付けて、回数の上限まで待ち直す。
- 作る書き込みが応答を返さずに切れたとき（タイムアウト・通信の切断・5xx）は、その実行の中では作り直さない。次に動かしたときに、区切りキーで探してから決める。
- `--dry-run` は、書く行と、止めた理由を出すだけで、Notion に書かない。

**残す状態**: 書き済みかどうかは、Notion の区切りキーと要約値で決めます。CLI は手元に状態のファイルを持ちません。書き終えたファイルを消すか移すかは、使う人が決めます。

**Notion に残るもの**: 検査を通った記録が、そのワークスペースに残ります。どの DB に書くか、誰が読めるかは、CLI を動かす人が決めて確かめるものです（PRIVACY.md に書く）。

## 既知の限界

- 保存した区切りは、拡張から取り消せない。保存したあとに「必ず伏せる語」を足しても、ファイルには残っている。保存の前のプレビューで確かめる。
- 未判定の期待結果を置いたままだと、そこから先は途中の区切りとして出せない。その間に上限に当たれば、今と同じく古いステップから消える（`trimmed`）。8 割の知らせは、未判定があることも示す。
- 区切りに入った NG のバグチケットは、保存の前に作らなければ、あとから作れない。
- 保存できたかどうかは、拡張から確かめられない。テスターが「はい」と答えた区切りは、ファイルが無くても手元から消える。
- 保存のあいだに範囲のステップが変わると、もう一度保存する必要がある。古いファイルを消し忘れると、CLI がその記録を書かずに止める。
- 区切りの先頭の期待結果は、前の区切りの最後の操作の結果として扱われない。
- Notion に書かれるのは、最後の区切りまで保存した記録だけ。記録の途中では Notion に無い。
- 作る書き込みが応答なしで切れたあと、Notion の検索にすぐ出ないと、次の実行で同じ区切りの行が 2 つできることがある。CLI は次の実行でそれを見つけて知らせる（自動では直さない）。

## 実装の順

1. ADR 0003 に M6〜M8 を足す。続けて、次を実装する。
   - `seq`
   - 送信データ v6（`part`・`commercialSeen`・出口の検査）
   - `describe.js` の、区切りの終わりとメモの環境を決める関数
   - `shared/record.js` の `PREPARE_PART`・`COMMIT_PART`、台帳と要約（上限・`fitRecord`）、`SET_VERDICT` の `SENT`、閉じた記録
   - worker のメッセージ
   - テスト（payload・record・worker）
2. サイドパネル: 「ここまでを保存して手元から消す」、区切りのプレビュー（NG のチケットのボタン）、保存の確かめと `COMMIT_PART`、8 割の知らせ。E2E は、区切りを保存して手元から消え、記録が続くところまで。
3. 書式 A・B を台帳・要約・手元のステップから作る。ほかの出口の書き添え。
4. `tools/notion-sync.mjs`（起動の条件・ロック・DB の確認・書く記録の選び方・区切りキーで探して作る・速さの上限・`--dry-run`）と、そのテスト（Notion の API は偽物で置き換える）。README・PRIVACY・FORMAT。

## 決めなかったこと

- 区切りを、自動で出すこと（プレビューの約束を変えるので、しない）。
- 出した区切りの判定を、あとから付け直すこと（オーナー判断で持たない）。
- 拡張から Notion や中継へ、区切りを直接送ること（2026-11-06 の判断で持たない）。
- 記録の途中の区切りを、Notion に先に書くこと。
- CLI が書式 A・B を作ること（書式は拡張の中だけで作る、ADR 0005）。
