# 0006 記録を区切りごとに送る（手元の上限を超えて記録を続ける）

- 状態: 提案
- 日付: 2026-11-05
- 関連: ADR 0001（商用環境）、ADR 0003（保証の表）、ADR 0005（書式 A・B、期待結果と判定）、`tools/receiver.mjs`

## 背景

記録は `chrome.storage.session`（メモリだけ。ブラウザを閉じると消える）にあり、1 つの記録は 500 ステップ（`LIMITS.steps`）・6 MiB（`LIMITS.storeBytes`）までです。これを超えると古いステップから消えて `trimmed` が付き、長い探索テストでは始めの方の操作が残りません。

上限を上げるとメモリの負担がそのまま増えます。そこで、記録の途中でそこまでのステップを送信先に送り、受け取れたら手元から消して記録を続けられるようにします。送信先の例は Notion の DB で、手元の中継が書きます。

## 決めたこと（オーナー判断 2026-11-05）

- **送る前に必ずプレビューを見る**約束は変えない。自動で送り続けない。
- きっかけは手動の「ここまでを送る」と、上限の 8 割（ステップ数か大きさのどちらか）でのパネルの知らせ。知らせはプレビューを自動で開かない。
- 途中の区切りは**最初の未判定の期待結果の手前まで**。送ったあとに判定を付け直す仕組みは持たない。**記録を止めたあとの最後の区切りだけは、未判定を含めてよい**。
- 書式 A・B（バグチケット・実施記録）は拡張の中だけで作る（ADR 0005 のまま）。そのため:
  - 送った区切りの**小さな要約**を手元に残し、実施記録は記録全体で作る。
  - NG の期待結果を含む区切りは、**送る前にそのバグチケットを作らせる**（下の「区切りのプレビュー」）。送ったあとは、その NG のチケットは作れない。
- Notion へは拡張から直接書かない。手元の中継（`tools/receiver.mjs` を拡張）が、受信の検査を通したあとに書く。トークンは中継の環境変数に置く。拡張の送信は汎用の `POST` のまま。
- 中継は、検査を通した区切りを**中継のディスクに保存できたときに 2xx を返す**。Notion にはその保存から順に書く（書けなかったものは保存に残り、書き直せる）。
- Notion の DB は**区切り 1 つを 1 行**にし、記録 ID で束ねる。

## ステップの通し番号

ステップを記録に足すとき、worker が手元だけで使う通し番号 `seq` を振ります（1 から。記録の中で増えるだけで、消しても振り直さない）。送信データの `steps[].n` は、区切りの送信ではこの `seq` です。

上限で古いステップが落ちても、テスターがステップを消しても、残ったステップの番号は変わりません。送った範囲と手元の照合、区切りの番号、再送の上書きは、すべてこの番号で行います（位置で数えると、落ちたステップの分だけずれて別のステップを送り直してしまう）。

区切りでない送信（今の全体の送信）の `n` は今と同じく 1 からの位置です。

## 区切り

区切りは、手元に残っているステップの先頭から、決めた位置までの連続したステップです。

- 終わりの位置は、**プレビューを作る時点**で決める。基準はその時点の最後のステップで、次の規則で前に寄せる（後ろへは延ばさない）。
  1. 途中の区切りは、**最初の未判定の期待結果の手前まで**。期待結果は、テスターがサイドパネルで書いた種類の無いメモ（ADR 0005 の `isExpectation`）。判定（`verdict`）の無いものが未判定。ページからの申告（`source: agent`）は判定を持たないので数えない。
  2. 最後のステップが人の操作・`key`・`tool` で、その操作から 4 秒（`FOLLOW_MS`）たっていなければ、たつまで待ってから決める（直後の遷移が、操作と別の区切りに分かれないように）。
  3. 区切りの最後が操作で、その直後の遷移がその操作の結果にあたるなら、遷移も区切りに入れる。区切りの終わりを決める関数は `describe.js` に置き、簡易手順・Gherkin が操作と遷移・通知を結びつけるのと同じ規則（同じタブ・4 秒・間の通知は操作の文脈を切らない）を共有する。ほかの場所で規則を作り直さない。操作の後の通知（`notice`）も、次の操作の手前まで区切りに入れる。1 で前に寄せたためにこの規則が未判定を越えるときは、操作の手前まで寄せる。
- 途中の区切りが空になるとき（先頭が未判定の期待結果）は送れない。パネルは「先に判定を付けてください」と、その期待結果を示す。
- **最後の区切り**（`final: true`）は、記録を止めたあとにだけ送れる。1 の規則は当てはめない（未判定を含めてよい）。手元に残ったステップが無くても送れる（ステップ 0 件の終了の区切り。`from` は次の番号）。

## 区切りのプレビューと予約

送る区切りは、プレビューから手元で消すまで**予約**して凍結します。送った中身と手元で消す中身が食い違う道（別のパネルの予約、上限による脱落、削除、判定の変更）を、照合で見つけるのではなく、起きないようにするためです。

1. パネルは worker に `PREPARE_PART` を送る。worker は書き込みの列の中で区切りの範囲を決め、範囲（`index`・`from`・最後の `seq`）と、区切りのステップを JSON にしたものの要約値（SHA-256）を予約として記録に保存して返す。
   - 予約は 1 つの記録に同時に 1 つだけ。予約があるあいだの `PREPARE_PART` は断る（黙って置き換えない）。予約は、`COMMIT_PART` か、パネルからの明示の取り消し（`CANCEL_PART`。下の 6）でだけ外れる。
2. 予約のあいだ、worker は予約したステップを凍結する。
   - テスターの削除（`DELETE_STEP`）と判定の変更（`SET_VERDICT`）が予約したステップに当たれば、`RESERVED` を返して変えない。パネルは「送信の準備中です。送るか取り消してから」と出す。
   - 上限（ステップ数・大きさ・サイトごと）で古いステップを落とすとき、予約したステップは落とさず、その後ろの古いものから落とす。落とせるものが無ければ、新しいステップを記録しない（`trimmed` を付ける）。
3. パネルはその範囲で送信データを作り、出口の検査をかけてプレビューする。送信データの `part.digest` に予約の要約値を入れる。区切りに NG の期待結果があれば、プレビューに **NG ごとのバグチケットのコピー・保存のボタン**を出し、まだどれも作っていなければ、送信の前に「チケットを作らずに送ると、あとから作れません」と確かめる。
4. 送る直前の照合は、記録全体の版（`revision`）ではなく、予約と、区切りのステップの要約値で行う（記録中は新しいステップが届き続けるので、記録全体で比べると送れない）。
5. 送信が 2xx で返り、応答の要約値が予約と同じなら、パネルは worker に `COMMIT_PART`（記録 ID・`index`・要約値）を送る。worker は書き込みの列の中で予約と一致することを確かめ、区切りのステップを消し、要約を足し、次の `index`・`from` を進め、予約を外し、`revision` を進める（手で編集した簡易手順の下書きは古いものになる）。
6. 送信が失敗したとき・2xx 以外のときは、予約を残したまま、パネルが「もう一度送る」「取り消す」を出す。パネルが閉じても予約は残り、次に開いたパネルが同じ 2 つを出す。
   - もう一度送ると、同じ `index` と要約値の区切りになる。受け取る側は、同じ記録 ID・`index`・要約値なら、もう受け取っていても成功を返す（冪等）。
   - 取り消すと予約が外れ、凍結も解ける。取り消した区切りがすでに受け取られていた（2xx の応答が届く前にパネルが閉じた）ときは、次に同じ `index` で違う中身を送ると、受け取る側が 409 を返す。そのときパネルは「送信先に同じ番号の別の中身がある」と出し、worker は `index` だけを進めて、ステップは消さずに次の番号で送り直す。送信先では、2 つの区切りが同じ `seq` を含む（`seq` で重なりが分かる。既知の限界）。
7. 送った期待結果に判定を付けようとすると（`SET_VERDICT`）、worker は `SENT` を返し、パネルは「送信済みのため変更できない」と出す。

## 送信データ（v6）

送信データを v6 に上げ、`recording.part` と `recording.commercialSeen` を足します（ADR 0003 に M6・M7 の行を足してから実装する）。

```json
"recording": {
  "id": "rec-…",
  "part": { "index": 2, "from": 181, "final": false, "digest": "…", "continuesAt": ["https://site-1.invalid/list"] },
  "commercialSeen": true,
  "steps": [ { "n": 181, … }, … ],
  …
}
```

- `part.index`: 区切りの番号。1 から、同じ記録で送った順に増える。
- `part.from`: この区切りの最初の `seq`。`steps[].n` は `from` 以上で、増える順に並ぶ（上限で落ちたりテスターが消したりした番号は飛ぶ）。
- `part.final`: 記録を止めたあとの最後の区切りなら `true`。
- `part.digest`: 予約の要約値（区切りのステップの SHA-256、16 進 64 字）。受け取る側の冪等の判定に使う。
- `part.continuesAt`: 2 つ目以降の区切りで、前の区切りの最後の画面（URL を持つ最後のステップの伏せた URL。ステップの `url` と同じ形）。前の区切りで URL を持つステップが無ければ無い。
- `commercialSeen`: この記録で、商用環境のステップを一度でも記録したか。サイドパネルのメモの環境（ADR 0001）を決めるのは `describe.js` の 1 つの関数だけにし、「`commercialSeen` か、残っているステップに商用がある」で決める。worker のメモの伏せ方（`cleanStep`）・`buildPayload`・`checkPayload` はどれもこの関数を使う（今は残っているステップだけで決めているので、商用のステップを送って消すと、そのあとのメモが緩く伏せられる）。`checkPayload` の検査は防波堤で、作る側の判定の代わりにしない。
- `part` が無い送信データは、今と同じく記録全体。区切りを 1 つでも送った記録は、残りも区切りとしてだけ送れる。
- そのほかの欄の作り方:
  - `startUrl`・`reproduction`（Markdown・Gherkin）は、その区切りのステップだけから作る。2 つ目以降の区切りの始まりの画面は `part.continuesAt`（前の区切りの最後の画面）にし、「区切り N の続き。前の区切りの操作をすべて終えた状態で、この画面から」と書く（Gherkin の `Background` と簡易手順の前提）。区切りの中の後のステップの URL を始まりにはしない（テスターがいたのは前の区切りの最後の画面のため）。`continuesAt` が無ければ「前の区切りの最後の画面は記録に無い」と書く。
  - `endedAt`・`notTested` は最後の区切りにだけ入る。`scope`・`targetVersion` はどの区切りにも入る。
  - `privacy.redactions` と `hostsAliased` は記録の始めからの累計。受け取る側は、最後に受け取った区切りの値を使う。
  - 別名（`site-N.invalid`）の対応表は送ったあとも手元に残す。区切りをまたいでも、同じホストは同じ別名になる。
  - `trimmed` は記録全体の印のまま。
  - `webmcpTools` は送る時点の一覧。

### 出口の検査

区切りの送信データにも `checkPayload` と `finalScan` をかけます。`checkPayload` は v6 で次も確かめます。

- `part.index`・`part.from` は 1 以上の整数、`final` は真偽値、`digest` は 16 進 64 字、`continuesAt` は URL の形（`index` が 1 なら無い）。
- `steps[].n` は `from` 以上で、増える順（同じ番号が無い）。
- `final` が `false` なら `endedAt`・`notTested` が無い。`final` が `true` なら `endedAt` がある。
- `final` が `false` の区切りに、未判定の期待結果が無い。
- ステップ 0 件は `final` のときだけ。
- サイドパネルのメモの環境が、`commercialSeen` と手元のステップから決まるものと合う。

## 手元に残す要約

送った区切りごとに、次だけを手元に残します（記録の `sent` 欄。送信データには入れない）。

- 区切りの `index`・最初と最後の `seq`・送った日時。
- 期待結果: `ref`・文・判定・実際の結果・画面（ADR 0005 の「期待結果の位置」の伏せた URL）。
- 画面ごとの数: 伏せた URL の移り変わりと、それぞれの「記録された操作・ツール呼び出し・ページからの申告」の数（ADR 0005 の `screenParts`）。区切りの境目で同じ画面が続くときは、次の区切りの最初の画面とまとめる。
- 探索メモ（種類のあるメモ）の文と種類。

要約の形は `shared/payload.js` に送信データと同じ書き方で定義し（ADR 0003 に M8 の行を足す）、書式 A・B に使う前に、送信データと同じく構造の検査をかけます（要約だけ構造の検査を通らずに出口へ出ることがないように）。要約は区切りのステップから worker が作り、文は伏せたあとの runs のまま持ちます。

- 判定の数: 送った期待結果の OK・NG・未判定の数の累計（`sentTotals`）。これは消さない。

上限: 期待結果と探索メモは合わせて 500 件、画面は 500 件。要約全体も記録の大きさ（`storeBytes`）に数え、`fitRecord` は手元のステップ（予約したものを除く）より先に要約の古い詳細から消す。詳細を消したら `trimmed` を付ける。`sentTotals` は消さないので、実施記録の結論（NG があれば「問題あり」）は詳細が欠けても正しく決まる。詳細が欠けているときは、NG が 0 件でも「確かめた範囲で問題なし」とは書かず、「判定の詳細の一部が欠けている（OK n 件・NG 0 件・未判定 m 件）」と書く。

### 書式 A・B と、ほかの出口

- **実施記録（書式 B）**: 結論は `sentTotals` と手元のステップから、確かめたこと・見つけたこと・画面ごとの数は、要約と手元のステップを合わせて作る。付録（記録したステップ）は手元のステップだけで、その前に「ステップ 1〜M は区切り 1〜N として送信済み」と書く。
- **バグチケット（書式 A）**: NG の期待結果が手元にあるときだけ作れる。再現手順は手元のステップから作り、先頭に「ステップ 1〜M は区切り 1〜N として送信済み。その続きから」と書く。送った区切りの NG は、送る前のプレビューで作る（上の「区切りのプレビューと予約」）。送ったあとはパネルの一覧に出さない。
- **JSON の保存・Markdown・Gherkin・Playwright の下書きのコピー**: 手元に残っているステップだけで作り、送信済みの区切りがあることを書き添える。区切りを送った記録の JSON の保存は、次に送る区切りと同じ形（`part` 付き）にする。

## 中継と Notion

`tools/receiver.mjs` に、Notion へ書く設定を足します。

- 起動の条件: `NOTION_TOKEN` と `NOTION_DATA_SOURCE_ID`（Notion の DB の data source の ID。今の Notion API で行を探し、列を読むのに使う ID）を渡したときだけ Notion に書く。そのときは、受信の認証（`OPSCRIBE_TOKEN`）と、登録語・実ホスト名の一覧（`OPSCRIBE_KEYWORDS_FILE`）も**必須**にし、無ければ起動しない（中継の `finalScan` は、一覧が無いと登録語と実ホスト名を探せないため。Notion は外部のサービス）。
- 受け取った送信データに今と同じ 2 つの検査をかけ、どちらかで検出があれば 422 を返す。
- 通ったものを `recordings/<記録 ID>/part-<index>.json` に保存し、**保存できたら 2xx を返す**。応答の本文に `part.digest` を返す。
  - 同じ記録 ID と `index` がもう保存されていれば、`digest` が同じなら保存し直さずに 2xx（冪等）、違えば 409 を返して上書きしない。
- Notion には、保存から順に 1 本の列で書く（速さの上限に合わせる）。**Notion は新しい出口**なので、書く直前に、保存した送信データにもう一度 `checkPayload` をかけ、実際に書く列の値と本文のブロックの文字すべてに `finalScan` をかける。どちらかで検出があれば書かず、書けないものとして残す。書けたかどうかは保存の横に記録し、書けていないものは中継の起動時と一定の間隔で書き直す。中継は、Notion に届いていない区切りの一覧を出せる（`GET /status`、127.0.0.1 のみ）。
- DB の 1 行が 1 つの区切り。
  - 固有の列「区切りキー」（`<記録 ID>:<index>`）で行を探し、あれば更新、無ければ作る。行を消して作り直すことはしない（Notion のページは消せず、ゴミ箱と履歴に残るため）。
  - 更新のときは、列を書き換え、本文のブロックを入れ替える。入れ替えで外したブロックも Notion のゴミ箱と履歴に残る（PRIVACY.md に書く）。入れ替えは何回かの書き込みに分かれ、途中で止まりうるので、書いたブロックの ID と段階を保存の横に残し、書き直すときはそこから続ける。
  - そのほかの列: 記録 ID・区切りの番号・最初と最後のステップの番号・送信日時・環境（`coverage`）・NG の数・最後の区切りか。
  - 起動時に、DB の data source から列の **property ID と型**を読んで確かめ、合わなければ起動しない（列の名前は人が変えられるため）。`Notion-Version` は中継の中で固定する。
  - 本文: Gherkin と属性表をコードのブロックで入れる。Notion の上限（rich text 1 つは 2000 字、配列は 100 要素、1 回の書き込みは 1000 ブロック・500 KB）に合わせて分けて書く。
  - 429 と 529 は `Retry-After` に従い、ジッターを付けて、回数の上限まで待ち直す。上限を超えたら書けていないものとして残す。

Notion に書くと、検査を通った記録がそのワークスペースに残ります。どの DB に書くか、誰が読めるかは、中継を動かす人が決めて確かめるものです（PRIVACY.md に書く）。

## 既知の限界

- 送った区切りは、あとから消せない。送ったあとに「必ず伏せる語」を足しても、送信先には届いている。送る前のプレビューで確かめる。
- 未判定の期待結果を置いたままだと、そこから先は途中の区切りとして送れない。その間に上限に当たれば、今と同じく古いステップから消える（`trimmed`）。8 割の知らせは、未判定があることも示す。
- 送った NG のバグチケットは、送る前に作らなければ、あとから作れない。
- 区切りの先頭の期待結果は、前の区切りの最後の操作の結果として扱われない。
- 送信が 2xx で返ったあと、`COMMIT_PART` の前にパネルを閉じると、手元に残ったまま送信先にも届いている。次に開いたパネルで「もう一度送る」を選べば、受け取る側は冪等に成功を返し、手元から消える。「取り消す」を選んで違う中身を送ると、送信先には `seq` の重なる 2 つの区切りが残る。
- 予約のあいだに上限に当たると、予約したステップは落とさないので、新しいステップが記録されないことがある（`trimmed`）。予約は送るか取り消すまで残るので、長く置かない。
- 中継が 2xx を返したあと Notion に届くまでには時間がかかる。中継が止まっている間は、保存にだけある。
- 中継が 2xx を返したあとに Notion 側で行が消された、などは拡張から分からない。

## 実装の順

1. ADR 0003 に M6〜M8 を足す。`seq`、送信データ v6（`part`・`commercialSeen`・出口の検査）、`describe.js` に区切りの終わりとメモの環境を決める関数、`shared/record.js` に予約（凍結・`RESERVED`・上限で落とさない）・`COMMIT_PART`・`CANCEL_PART`・要約（上限・`sentTotals`・`fitRecord`）、`SET_VERDICT` の `SENT`。worker のメッセージ。テストは payload・record・worker。
2. 受信サーバ: v6 を受け付け、区切りを保存する（同じ要約値なら冪等、違えば 409）。サイドパネル: 「ここまでを送る」、区切りのプレビュー（NG のチケットのボタンと確認）、2xx のあとの `COMMIT_PART`、8 割の知らせ。E2E（受信サーバまで）。
3. 書式 A・B を要約と手元のステップから作る。ほかの出口の書き添え。
4. 中継の Notion 書き込み（起動の条件・DB の確認・区切りキーで更新・分けて書く・書き直し・速さの上限・`/status`）と README・PRIVACY・FORMAT。

## 決めなかったこと

- 区切りを、記録を止めずに自動で送ること（プレビューの約束を変えるので、しない）。
- 送った区切りの判定を、あとから更新して送ること（オーナー判断で持たない）。
- 送信先から区切りを取り戻して、手元で書式を作り直すこと。
- 中継が書式 A・B を作ること（書式は拡張の中だけで作る、ADR 0005）。
