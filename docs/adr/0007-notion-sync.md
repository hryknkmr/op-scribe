# 0007 区切りのファイルを Notion に書く CLI

- 状態: 提案（未決の論点あり）
- 日付: 2026-11-06
- 関連: ADR 0006（区切りのファイル）、ADR 0003（保証の表）、ADR 0005（書式は拡張の中だけで作る）

## 背景

ADR 0006 で、拡張は記録を区切りごとのファイル（`<記録 ID>.part-<index>.opscribe.json`、送信データ v6）に保存して手元から消すようにしました。この ADR は、そのファイルを読んで Notion の DB に書く、手元の CLI（`tools/notion-sync.mjs`）を決めます。拡張とは別に、テスターが手で動かします。拡張と CLI の約束は、ADR 0006 の「区切りのファイル」と「出口の検査」だけです。

もとは ADR 0006 の一部でしたが、7 回のレビューで、新しく見つかる問題が拡張の中の状態と、CLI と Notion の制約の 2 つに分かれていたので、分けました（オーナー判断 2026-11-06）。

## 決めたこと

オーナー判断（2026-11-05・11-06、ADR 0006 から引き継ぐ）:

- Notion の DB は、区切り 1 つを 1 行にし、記録 ID で束ねる。
- Notion へは拡張から書かない。この CLI が、保存したファイルを読んで書く。
- 「区切り 1 つを 1 行」は CLI が守ろうとするもので、保証ではない。同じ区切りキーの行が 2 つ以上あれば、CLI が見つけて知らせる。CLI を動かすのは 1 か所にする（運用で決める）。
- CLI は書式 A・B を作らない（書式は拡張の中だけで作る、ADR 0005）。

## CLI

```sh
node tools/notion-sync.mjs <ファイルのあるフォルダ> [--dry-run]
```

保存した区切りのファイルを読み、Notion の DB に書く手元の CLI です。拡張とは別に、テスターが手で動かします。

```sh
node tools/notion-sync.mjs <ファイルのあるフォルダ> [--dry-run]
```

**起動の条件**:

- 環境変数 `NOTION_TOKEN`・`NOTION_DATA_SOURCE_ID`・`OPSCRIBE_KEYWORDS_FILE`（登録語・実ホスト名の一覧）がすべて要る。一覧が無いと、`finalScan` が登録語と実ホスト名を探せないため。
- 同じフォルダで 2 つ同時に動かさない。フォルダに `.notion-sync.lock` を排他で作り（作れなければ止まる）、終わったら消す。
- 起動時に、DB の data source から列の property ID と型を読んで確かめ、合わなければ止まる（列の名前は人が変えられるため）。`Notion-Version` は CLI の中で固定する。

**ファイルの検査**: `*.part-*.opscribe.json` を読み、それぞれに `checkPayload` と `finalScan` をかけます。検出があったファイルは書かずに知らせます。

**書く記録の選び方**（ファイルの中身だけで決める）:

- 記録 ID ごとに区切りを集め、次をすべて満たす記録だけを書く。
  - 番号が 1 から欠けずに続く。
  - 最後の区切り（`final: true`）がちょうど 1 つあり、それがいちばん大きい番号。
  - 区切り N+1 の `from` が、区切り N の `to` + 1。
  - 記録 ID・`startedAt`・`scope`・`targetVersion` がすべての区切りで同じ。`commercialSeen` は一度 `true` になったら戻らない。
  - 記録の始めからの累計（`privacy.redactions` の各数・`hostsAliased`）は減らない。`trimmed` は一度付いたら外れず、`other` から `user` へは変わっても戻らない。
  - 区切り N+1 の `continuesAt` が、区切り N の URL を持つ最後のステップの `url` と `env`（無ければ区切り N の `continuesAt`）と同じ。区切り N+1 が `continuesHidden` なら、`continuesAt` が無いことだけを確かめる（拡張が登録語に当たって入れなかったもの。ADR 0006）。
  - 区切り N+1 の `earlier.gaps` が、区切り 1〜N のどれかに `removed` があるかと同じ。
  - 区切り N+1 の `earlier` の `ok`・`ng` が、区切り 1〜N の期待結果の判定の数の合計と同じ（`parts`・`through` は `checkPayload` が確かめる）。
- 同じ記録 ID と番号のファイルが 2 つ以上あり、バイト列が違うときは、その記録は書かずに、ファイル名を挙げて知らせる。人がどちらかを消してから動かし直す（拡張は同じ名前に上書きするので、2 つになるのはファイルを移したときだけ）。
- 記録の途中の区切りを先に書くことはしない（書いたあとに同じ番号の別の中身が保存されると、食い違いが Notion に残るため）。

**Notion への書き方**:

- 1 つの区切りを 1 行にしようとする（保証ではない。上の「決めたこと」）。
  - 列「区切りキー」（`<記録 ID>:<index>`）を持つ。中身の要約値は Notion に書かない（`finalScan` が長い 16 進の文字列を ID として止めるため）。
  - そのほかの列は、記録 ID・区切りの番号・範囲（`from`・`to`）・ステップの数・環境（`coverage`）・NG の数・最後の区切りか。
- 書く前に、区切りキーで DB を探す。
  - 無ければ、列と本文のブロックを **1 回の書き込みで**作る。
  - 1 行あって、列の値と本文のブロックの文字が、このファイルから作るものとすべて同じなら、書き済みとして飛ばす。
  - 1 行あって 1 つでも違うとき、2 行以上あるときは、書かずに知らせる（人が Notion を直したときも含む）。
  - 行を更新したり、消して作り直したりはしない（Notion のページは消せず、ゴミ箱と履歴に残るため）。
- 本文は、Gherkin と属性表をコードのブロックで入れる。Notion の上限（rich text 1 つは 2000 字、配列は 100 要素、1 回の書き込みは 1000 ブロック・500 KB）に合わせて分ける。1 回の書き込みに収まらない区切りは、書かずに知らせる。
- **Notion は新しい出口**なので、実際に書く列の値と本文のブロックの文字すべてに、書く直前に `finalScan` をかける。検出があれば書かない。
- 書き込みは 1 本ずつ順に行う。429 と 529 は `Retry-After` に従い、ジッターを付けて、回数の上限まで待ち直す。
- 作る書き込みが応答を返さずに切れたとき（タイムアウト・通信の切断・5xx）は、その実行の中では作り直さない。次に動かしたときに、区切りキーで探してから決める。
- `--dry-run` は、書く行と、止めた理由を出すだけで、Notion に書かない。

**残す状態**: 書き済みかどうかは、Notion の区切りキーと範囲で決めます。CLI は手元に状態のファイルを持ちません。書き終えたファイルを消すか移すかは、使う人が決めます。

**Notion に残るもの**: 検査を通った記録が、そのワークスペースに残ります。どの DB に書くか、誰が読めるかは、CLI を動かす人が決めて確かめるものです（PRIVACY.md に書く）。

## 未決の論点

ADR 0006 の 7 回目のレビューで出た、CLI と Notion の側の問題です。決めるまで実装しません。

1. **最後の区切りが無い記録**: ブラウザの再起動や拡張の更新で記録が消えると（ADR 0006 の既知の限界）、最後の区切りは作れない。今の「最後の区切りまで揃った記録だけを書く」では、保存済みの区切りが Notion に届かない。
   - 案: CLI に、最後の区切りの無い記録を「打ち切り」として書く指定（例: `--close <記録 ID>`）を足し、Notion に未完と分かる列を付ける。
   - 案: 途中の区切りも先に書く（同じ番号の別の中身が後から保存されたときの扱いを決める必要がある）。
2. **1 回の書き込みに収まらない区切り**: 大きさの 8 割（約 4.8 MB）で区切ると、本文の Gherkin と属性表は Notion の 1 回の書き込み（500 KB）を超えうる。今の案では、その区切りはずっと書けない。
   - 案: 行を作ったあと、子ブロックを何回かに分けて足す（区切りキーと、書いたブロックの数で続きを決める）。1 回で作る原子性は失う。
   - 案: 本文は要約だけにし、Gherkin はファイルとして添付する（添付の大きさの上限と、添付への `finalScan` を決める）。
   - 案: 拡張が、区切りの大きさを Notion に収まる大きさまでに抑える（拡張が Notion の制約を知ることになる）。
3. **あとで足した登録語**: CLI の `finalScan` は CLI を動かす時点の一覧で検査するので、保存したときには通った区切りが CLI では止まりうる。そうなると、その記録の残りも書けない。止めたものをどう扱うか（その区切りだけ飛ばして書くか、記録全体を止めるか）。

## 既知の限界

- Notion に同じ区切りの行が 2 つできたら、CLI は知らせるだけで、直すのは人。
- 作る書き込みが応答なしで切れたあと、Notion の検索にすぐ出ないと、次の実行で同じ区切りの行が 2 つできることがある。CLI は次の実行でそれを見つけて知らせる（自動では直さない）。
- 同じ記録 ID と番号のファイルが 2 つあると（テスターがファイルを移したときなど）、その記録は書かない。

## 実装の順

1. 未決の論点を決める。
2. `tools/notion-sync.mjs`（起動の条件・ロック・DB の確認・書く記録の選び方・区切りキーで探して作る・速さの上限・`--dry-run`）と、そのテスト（Notion の API は偽物で置き換える）。
3. README・PRIVACY（Notion に残るもの）。

## 決めなかったこと

- 拡張から Notion や中継へ、区切りを直接送ること（ADR 0006）。
- Notion の行を更新したり、消して作り直したりすること。
