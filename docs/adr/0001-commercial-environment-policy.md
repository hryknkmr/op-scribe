# 0001. 商用環境だけを厳格に扱う伏せ方

- 状態: 採用（2026-10-31）
- 日付: 2026-10-31
- 関係: PR #6（伏せる規則の一本化）、PR #5 を分けた 1 本目

## 背景

- この拡張の目的は、ユーザーの操作を記録して再現手順にすることです。
- PR #6 では、すべての環境で「入力と URL の値は残し、パターンで伏せる」方針を採りました。
  - 伏せるのは、認証情報（全体）と、メール・電話・ID（一部）です。
- この方針でレビューを 20 ラウンドかけましたが、収束しませんでした。
  - 毎回、新しい抜けが見つかりました。例: 表記ゆれ、多重エンコード、入れ子の URL、未知の伏せ字、Unicode と不可視文字。
- 値を残す限り、パターンの抜けは尽きないと判断しました。

## オーナー決定（2026-10-31）

1. **記録対象を既定で外さない。** 記録したいのはユーザー操作であり、既定で中身を外すのは目的と相反する。
2. **厳格に扱うのは、リアルな商用環境だけ。** beta・staging などには及ばない。
3. **商用環境は、設定に登録したホストで見分ける。**
   - 設定の欄は「商用環境のホスト」。1 行 1 件、`*.example.com` も書ける。
   - 登録していないホストは、すべて商用環境ではない扱い。
4. **商用環境での扱い:**
   - 自由入力は文字数だけ（`[[text:12]]`）にする。
   - 検索欄の値と、選択肢の値は残す。
   - URL のクエリ値は、英数字と `. _ -` だけで 24 文字以内なら残し、それ以外は `[[v]]` にする。
   - フラグメントは、SPA のルート（`#/settings`）だけを残す。
5. **それ以外の環境での扱い:** PR #6 の方針のまま。入力と URL の値は残し、認証情報は全体を、メール・電話・ID は一部だけ伏せる。
   - 補足（2026-10-31 オーナー確認、ADR 0003）: メール・電話・ID の欄で、値全体が 1 つのアドレス・番号の形でないときは、一部だけ伏せる位置が決まらないので全体を伏せる。
6. **どの環境でも共通:**
   - 許可していないホストは別名（`site-N.invalid`）にする。
   - 登録語は伏せる。
   - 出口（送信・コピー・保存）では `finalScan` をかける。
7. **運用の一貫性は、Codex とのレビューで詳細を決める。**

## 論点と推奨（Codex との設計レビュー）

レビューの全文は、作業メモ `tmp/cxm6/policy-output.txt` にあります（リポジトリには入りません）。

| 論点 | 推奨 | 理由 |
| --- | --- | --- |
| 1. 商用かどうかの判定 | ステップは、トップのページのホストと、操作が起きたフレームのホストのどちらかが商用なら商用。値の中の URL は、さらにその URL 自身のホストでも判定する。記録開始時のタブで固定しない | サイト間の移動・iframe・文中の URL を、それぞれ実際の出どころで扱える |
| 2. 厳格にする範囲 | 自由入力・contenteditable・利用者が書く期待結果（メモ）は文字数だけ。WebMCP の引数は、文字列・数値を伏せ字にする。検索欄・選択肢・操作した要素の名前は、通常の規則で伏せてから残す | 抜けが尽きない原因である自由な値を、主な経路から取り除く。再現に要るものは残す |
| URL のパスとフラグメント | クエリと同じ「短い安全な文字だけ残す」規則を、パスの区切りごとにも当てる。ルートと判定できないフラグメントは `[[v]]`。認証情報の規則は常に優先する | パス全体を伏せるより役に立ち、形で ID を探すより検証しやすい |
| 3. content script と worker の一貫性 | content script が生の値をページ外に出す前に伏せ、`valueClass`（text・search・choice など）だけを付ける。worker は送信元の情報から商用かどうかを自分で判定し直し、商用の text が `[[text:N]]` でなければ `[[v]]` にする | 生の値をページ外に出さず、worker が欄の種類を知らない問題も補える |
| 4. 記録中の設定変更 | 商用環境のホストと実名許可のホストは、記録開始時の値で固定する。登録語は、足した分だけすぐ効かせる。商用と beta をまたぐ記録は、ステップごとに扱う | 1 つの記録の中で規則が揺れない |
| 5. 出口の検査 | 今のパターン検査に、商用ステップの構造の検査を足す（決まった伏せ字か、URL が商用の規則を通しても変わらないか、扱いの印が欠けていないか）。Gherkin は出口で記録から作り直す | 文章をもう一度パターンで探すのではなく、「生の値が無い」ことを確かめられる |
| 6. 送信データの印 | `privacy.policy`（方針の名前と版）、`coverage`（商用だけ / 商用以外だけ / 混在）、ステップごとの扱いを出す。商用ホストの一覧そのものは出さない。スキーマの版を上げる | 混在と検索の例外を、受け取る側が誤解しない |
| 7. 商用ホストと実名許可ホストの組み合わせ | 2 つのリストを独立させる。両方に入っているホストは「実名で、値は厳格」 | 「ホスト名を出してよい」と「値を緩めてよい」を混同しない |
| 8. 過去の抜けの整理 | 商用環境の自由入力・メモ・WebMCP 引数では、値を残さないので抜けは構造的に起きない。検索欄・選択肢・要素の名前・商用以外の環境では、今のパターン規則と出口の検査を続ける | すべて解決したと誤解しない。残る範囲を限定して説明できる |

### 残るリスク（推奨どおりでも）

- 商用環境のホストを登録し忘れる、またはワイルドカードを誤る。
- beta・staging に本物の商用データが入っている。
- 検索欄・選択肢・要素の名前に入った人名などの自然な文。
- 手で編集した Markdown から入り込む値。

## 決定（2026-10-31 オーナー確認）

上の推奨を基本に採り、次の点は次のように決めました。

| 点 | 決定 | Codex の推奨との違い |
| --- | --- | --- |
| 商用環境でのメモ（利用者が書く期待結果） | **残す**（通常の規則で伏せてから） | 推奨は文字数だけ。メモは利用者が意図して書く再現の要点なので残す |
| 商用環境での WebMCP の文字列の引数 | 文字数だけ | 同じ |
| 検索欄とみなす条件 | DOM の意味だけ（`type=search`・`role=searchbox`・`role=search` の中） | 同じ |
| 商用環境での URL のパス | クエリと同じく、区切りごとに短い英数字だけ残す（ID は一部だけ伏せる） | 同じ |
| 手で編集した Gherkin | 商用環境を含む記録では、出口で記録から作り直す（手の編集は使わない）。Markdown の手の編集は最終検査だけ | 推奨は Markdown も送れなくする。使い勝手を優先し、Markdown は最終検査に任せる |
| 送信データ | スキーマを `op-scribe.recording/v2` に上げ、方針の名前・範囲（商用だけ / 商用以外だけ / 混在）・ステップごとの扱いを入れる | 同じ |

以前の設定（全環境で厳格）を使っていた利用者は、更新後、商用環境のホストを登録するまで値が残る扱いになります。決定 1（既定で記録の中身を外さない）に沿うものとして、保守的な扱いには戻しません。代わりに、サイドパネルで一度、扱いが変わったことと登録を促す表示を出します（レビュー 26 ラウンド目の指摘への対応）。設定を一度も保存していなかった利用者（旧版の既定は厳格）にも、更新時に worker が印を付けて同じ表示を出します（30 ラウンド目）。

実装では、論点 1（判定はトップのページのホスト。iframe には今は注入しないので対象外）、論点 3（worker は送信元から判定し直す）、論点 4（記録開始時の設定で固定）、論点 7（2 つのリストは独立）を推奨どおりに入れます。
