# 0005 読み手ごとの出力の書式（バグチケットと実施記録）

- 状態: 採用（オーナー 2026-11-02。実装は未着手）
- 日付: 2026-11-02
- 関連: Issue #42、ADR 0003（保証の表）、PR #45（操作後の通知 `notice`。main に入っている）。受動記録の範囲（ADR 0004）は別のブランチで作業中で、この ADR はそれに依らない

## 背景

op-scribe の出力は今、簡易手順（Markdown）・Gherkin と属性表・送信用の JSON の 3 つです。どれも「記録した操作を並べたもの」で、誰が何のために読むかを前提にしていません。

使う側の目的は次の 3 つです（オーナー、2026-11-02）。

| 目的 | 読み手 | 知りたいこと |
| --- | --- | --- |
| 1. 不具合の再現方法を伝える | 開発者 | どうすれば同じことが起きるか、何が期待と違ったか |
| 2. テスト活動を評価する | 上長 | 何を、どこまで、どう試したか、何が見つかったか |
| 3. 問題が無かったときの根拠を残す | 上長・PdM・開発チーム | 何を確かめて問題なしと判断したか、何はやっていないか |

2 と 3 は、問題があったかどうかで結果の欄が変わるだけで、見せるものは同じです。そこで出力の書式を、**バグチケット**（目的 1）と**実施記録**（目的 2・3）の 2 つにします。

## 決めたこと（オーナー判断 2026-11-02）

- バグチケットの欄は「概要」「再現手順」「期待結果」「実際の結果」「環境・対象バージョン」。再現率・重要度・添付は持たない。
- 実施記録は 1 回の記録（開始から停止まで）ごとに 1 つ。複数の記録を束ねるのは、人が別の場所で行う。
- 期待結果ごとに判定（OK / NG）を付ける。
- 「対象と範囲」と「対象のバージョン」は記録を始めるときに、「やっていないこと」は止めるときに、テスターが書く（どれも空欄でよい）。
- チケットと実施記録の対応は、期待結果ごとの変わらない短い ID で取る。
- NG にするときは「実際の結果」を必須にする。
- 送信データを v4 に上げても、受信サーバは v3 も受け付ける。
- 書式 A・B は拡張の中だけで作る。受け取る側には記録（JSON）だけを渡し、同じ文を作り直せることは保証しない（オーナー判断 2026-11-02、仕様を小さくするため）。

## 書式 A: バグチケット

NG と判定した期待結果 1 つにつき 1 枚。記録の中に NG が 2 つあれば 2 枚作れる。サイドパネルは NG ごとに 1 枚ずつ別々にコピー・保存できるようにし、複数の NG をつなげた 1 つの文は作らない。記録中でも作れる（NG を見つけたその場で起票できる）。書式 A・B は、コピー・保存のたびにその時点の記録から作り直す。手で編集した簡易手順の下書きは使わないので、下書きが古いときに出力を止める今の仕組みは、書式 A・B には当てはめない。

| 欄 | 作り方 |
| --- | --- |
| 概要 | 決まった型「[{ID}] 『{期待結果}』が期待どおりにならない（{画面}）」。{ID} は下の「チケットとの対応」の ID。{画面} は下の「期待結果の位置」で決まる伏せた URL（無ければ「画面不明」）。期待結果の文を否定形に言い換えることはしない（決まった手順では正しく言い換えられないため）。テスターが書き換える前提の下書き |
| 再現手順 | 記録の始めから、NG の期待結果の直前のステップまで（下の「期待結果の位置」）。今の簡易手順と同じ文（テンプレート）。伏せた入力は「‹任意の文字列 6文字›」のように、用意する値として書く |
| 期待結果 | NG の期待結果の文 |
| 実際の結果 | NG を付けるときにテスターが書く文（新しい欄、NG では必須）。その後ろに「画面に出た通知」として、NG の期待結果より前で最も近い、人の操作・`tool`・遷移（`navigate`）のどれかのステップから、その期待結果までの間に記録された通知（`notice`）を（そのようなステップが無ければ記録の始めから）、記録の順に今のテンプレートの文で添える（無ければ添えない） |
| 環境・対象バージョン | ブラウザ・OS・言語（今の `environment`）と、記録を始めるときに書いた対象のバージョン |

### 期待結果の位置

期待結果のメモは、ステップの並びの中の位置で、直前の操作に付く（今の簡易手順・Gherkin と同じ）。どの操作に付くかを指す欄は持たない（期待結果そのものを指す `ref` は下の「チケットとの対応」）。

- 再現手順は、そのメモより前にあるステップを、今の簡易手順と同じ規則で文にしたもの。操作の直後の遷移は、再現する人の操作ではなく結果なので、手順にせず畳む。連続する同じ URL の遷移は省く。期待結果・探索メモ・ページからの申告の期待結果は手順に入れない。操作の後に画面に出た通知（`notice`）も手順に入れず（今の簡易手順のように操作の観察として付けることもしない）、「実際の結果」にだけ添える。
- 画面は、そのメモより前で最も近い、URL を持つステップの URL。
- テスターがステップを削除したときは、残ったステップから作る（削除は意図したものとして扱う）。
- 記録に `trimmed`（上限のために worker がステップを保持できなかった印。値は `user` か `other`。下の組み合わせの制約）があるとき（どちらの値でも）、または先頭のステップが `navigate` でないとき（テスターが先頭を削除した）は、再現手順の先頭に「記録の一部が欠けている可能性がある」と書く（上限で消えるのは先頭とは限らない）。テスターが先頭から途中の `navigate` までを削除した場合は検知できない（削除は意図したものとして扱う）。
- 先頭の遷移は、今の簡易手順と同じく「{URL} を開く」という手順になる（`navigate → NG の期待結果` なら、再現手順はその 1 行。開いただけで起きる不具合も再現できる）。メモより前にステップが 1 つも無ければ（先頭を削除した場合など）、再現手順は「（記録された操作なし）」とする。

再現できる確かさ（Issue #42 の slice 3 の再生前のチェック）は、できたあとに「再現手順」の後ろへ注意として足す。

## 書式 B: 実施記録

1 回の記録につき 1 つ。記録を止めてから作る（終了の時刻と「やっていないこと」が決まってから）。記録中は作れない。

| 欄 | 作り方 |
| --- | --- |
| 対象と範囲 | 記録を始めるときにテスターが書いた文 |
| 対象のバージョン・環境 | 書式 A と同じ |
| 実施した時間 | 開始と終了の時刻を、記録の値（UTC の ISO 形式）のまま出し、差を分（切り捨て）で添える。`endedAt` が無い、または `startedAt` より前なら、実施記録は作らない |
| 実施した操作 | 伏せた URL の移り変わり。伏せた URL を変わった順に並べ（下の「画面ごとの流れと付録」）、それぞれで 3 種類を分けて数える。①記録された操作: `source: user` で種類が `click` `input` `select` `check` `upload` `key` `submit`。見出しは「記録された操作（ブラウザが人の操作として届けたもの）」とし、テスターの操作だと言い切らない（ページのスクリプトも `focus()` などで同じ印のステップを作れる。ADR 0003 の W7 の既知の限界）。②ツール呼び出し: 種類が `tool`（エージェントがページのツールを呼んだもの）。③ページからの申告: 種類が `note` で `source: agent`（ページが送った期待結果）。②③は①に数えない。遷移・通知（`notice`）・テスターのメモは数えない。操作の全文は付録に回す |
| 確かめたこと | テスターが書いた期待結果（`source: user`）の一覧を記録の順に。それぞれに ID・画面・判定（OK / NG / 未判定）と、NG なら実際の結果。NG のものには書式 A と同じ「画面に出た通知」を添え、「バグチケット [{ID}]」と書く（下の「チケットとの対応」）。ページが申告した期待結果は判定の対象にせず、ここには出さない（「実施した操作」の件数と付録にだけ出す。本文に節は作らない） |
| 見つけたこと | 探索メモ（不具合・疑問・気づき・次に試す）を種類ごとに |
| やっていないこと | 記録を止めるときにテスターが書いた文 |
| 結論 | テスターが書いた期待結果の判定と `trimmed` から、下の「結論の決め方」で作る。`trimmed` があれば（どちらの値でも）、実施記録の冒頭にも「記録の一部が上限で消えている（操作の数・画面・付録も一部）」と書く |

### 結論の決め方

上から順に当てはめ、最初に当たったものにする（OK・NG・未判定は、テスターが書いた期待結果の件数）。

| 条件 | 結論 |
| --- | --- |
| NG が 1 件以上 | 「問題あり（NG n 件）」。未判定があれば「（未判定 m 件）」、`trimmed` があれば（どちらの値でも）「（記録の一部が欠けている）」を後ろに足す |
| `trimmed` が `user` | 「判定なし（記録の一部が欠けている）」。消えたステップに NG や未判定があったかは分からないので、「問題なし」とは言わない。`trimmed` が `other` のときはこの行に当てず、下の行に進む（冒頭の警告は出る） |
| 期待結果が 0 件 | 「判定なし（期待結果が無い）」 |
| 未判定が 1 件以上 | 「判定なし（未判定 m 件）」 |
| ほか（全部 OK） | 「確かめた範囲で問題なし（OK n 件）」 |

### チケットとの対応

テスターが書いた期待結果（`note`・`kind` 無し・`source: user`）に、足したときに worker が短い ID（`ref`、`E-` と英小文字・数字 6 文字。例 `E-7f3a9k`）を付ける。ID は乱数（`crypto.getRandomValues`）で、今の記録に残っているステップの ID と重なれば引き直す。振った ID の履歴は持たない（約 22 億通りなので、削除や上限で消えた ID と同じものが同じ記録で出ることは実際上ない。起こり得ることは受け入れ、一意は保証しない）。順番や件数を表さない（連番にしない）ので、ほかの期待結果を削除しても変わらない。記録をまたぐと同じ ID があり得るので、対応は「記録 ID ＋ ID」で取る: バグチケットの末尾と実施記録の冒頭に記録 ID（今の送信データの `recording.id`）を出し、ID は両方の行に出す。対応を取れるのは、記録に残っているステップだけ。記録中にチケットを作ったあと、その期待結果が上限で消えたときは、実施記録にその ID は出ず、どのチケットの期待結果が消えたかは分からない（ID の履歴を持たないため。`trimmed: user` の警告だけが出る）。

### 画面ごとの流れと付録

- 区切りは記録の順に作る。URL を持つステップが直前の区切りと違う伏せた URL を持つとき、新しい区切りを始める（A → B → A は 3 つの区切り。同じ URL でもまとめない）。
- 区切りは伏せた URL で作るので、実際には違う画面でも伏せた URL が同じなら 1 つの区切りになる（パスの区切りが `[[v]]` になった、URL 全体が `[[url:invalid]]` になった、など）。そのため見出しは「伏せた URL の移り変わり」とし、区切りの数を「通った画面の数」とは書かない。
- URL を持たないステップは、その時点の区切りに入る。最初の URL より前にあれば、先頭の「画面不明」の区切りに入る。
- 各区切りには、そこで数えた操作の数を出す。0 件の区切りも出す（遷移しただけの画面も通った画面として見せる）。
- 付録は、記録の順に 1 ステップ 1 行の一覧。ステップを 1 つも省かず、まとめもしない（今の簡易手順は期待結果を前の操作にまとめ、遷移を畳み、探索メモを別の節に移すので、付録には使わない）。各行は「{順番}. {ステップの文}」で、文は今のテンプレートの 1 ステップの文と同じ。ページからの申告には「（ページからの申告）」、メモには「（期待結果: OK / NG / 未判定）」か探索メモの種類を付ける。

操作の数は欄に出すが、評価の指標としては扱わない（数を増やすこと自体が目的になりやすく、テストの質を表さないため）。

## 記録に足す欄

どれも、先に ADR 0003 の表に行を足し、`shared/payload.js` の `SHAPE` に入れてから出す。記録は `chrome.storage.session` にだけあり、Chrome は拡張を更新・再読み込みすると消すので、v4 より前の記録が新しい版の拡張に残ることはなく、移し替える処理は持たない。今の `op-scribe.recording/v3` は知らない欄を拒否するので、欄を足すときに版を `v4` に上げる（受信サーバ `tools/receiver.mjs`・`docs/FORMAT.md`・版のテストも合わせて直す）。受信サーバと `checkPayload` は v3 も受け付ける。ここで受け付けるのは形の検査（`SHAPE`）のこと。送られた Gherkin を記録から作り直して照合する検査（ADR 0003 の E3）は今と同じで、版に関係なく当てる。この ADR は Gherkin の作り方を変えないので、同じ拡張が作った v3 は通る。Gherkin の作り方が変わった後に古い拡張が作った送信データが照合で止まるのは今もある挙動で、この ADR では変えない。検査は版ごとに分ける:

| 制約 | v3 | v4 |
| --- | --- | --- |
| 新しい欄（`ref`・`verdict`・`actual`・`scope`・`targetVersion`・`notTested`・`trimmed`） | 1 つでもあれば拒否 | 下の組み合わせの制約で検査 |
| テスターが書いた期待結果に `ref` が必須 | 適用しない | 適用する |
| `endedAt` が `startedAt` 以後 | 適用しない（これまでどおり受け付ける） | 適用する（拒否） |

受け付ける版は `v3` と `v4` の 2 つだけ（`shared/payload.js` に一覧として書く）。v3 の形は、`SHAPE` から `since: 4` の欄を除いたもの。書式 A・B は拡張が今の記録（常に v4）から作るので、v3 から書式を作る処理は持たない。

| 欄 | どこに | 誰が書くか | 伏せ方（案） |
| --- | --- | --- | --- |
| 期待結果の ID `ref` | 期待結果のメモ（`kind` の無い `note`、`source: user`） | worker が足したときに振る | 決まった形 `^E-[0-9a-z]{6}$`（T6） |
| 判定 `verdict`（`ok` / `ng`） | 期待結果のメモ（`kind` の無い `note`） | サイドパネルで人だけ（`source: user`）。WebMCP のエージェントが足した期待結果には付けられない | 決まった値（T6） |
| 実際の結果 `actual` | NG の期待結果のメモ | 人だけ | メモと同じ（T1: 300 字・1 行・できる限りの検出） |
| 上限で欠けた印 `trimmed`（`user` / `other`） | 記録全体 | worker が付ける | 決まった値（ADR 0003 の M の行。記録全体の欄なので T6 ではない） |
| 対象と範囲 `scope` | 記録全体 | 人が開始時に | メモと同じ（T1） |
| 対象のバージョン `targetVersion` | 記録全体 | 人が開始時に | メモと同じ（T1）。80 字 |
| やっていないこと `notTested` | 記録全体 | 人が停止時に | メモと同じ（T1） |

欄の組み合わせの制約（ADR 0003 の行に書く。worker は合わない値を落として作らず、`checkPayload` と受信サーバは合わないものを拒否する）:

- `verdict` は、種類が `note`・`kind` が無い・`source: user` のステップにだけ付く。
- `ref` は、テスターが書いた期待結果（`note`・`kind` 無し・`source: user`）すべてに必ず付き（判定の前から）、ほかのステップには付かない。記録の中で重ならない。
- `verdict` は `ref` を持つステップにだけ付く（無ければ未判定）。
- `actual` は `verdict: ng` のステップに必ず付き、ほかのステップには付かない。伏せた後の文を描いて前後の空白を除いたものが空なら、付いていないものとして扱う（worker・`checkPayload`・受信サーバのどこでも同じ）。`actual` の無い `ng` への更新が届いたら、worker は更新全体を拒否し（`ok: false`）、そのステップの元の `verdict`・`actual` をそのまま残す。
- 判定の更新: サイドパネルは、表示している記録の ID（`recordingId`）と `ref` で期待結果を指して `verdict`・`actual` を送る。worker は `recordingId` が今の記録の ID と一致するときだけ、その記録から `ref` のステップを探して更新し、`ref` 自体は書き換えない（並びの位置では指さない。記録中に削除や上限でステップが消えても、別のステップを更新しないため。ただし `ref` は引き直しで再び出ることを受け入れているので（「チケットとの対応」）、これは確率的な性質で、保証ではない。記録の ID を付けるのは、止めて新しい記録を始めたあとに古い画面から届いた更新を、新しい記録の同じ ID のステップに当てないため）。一致しない、または見つからなければ何もしない。worker は、更新したかどうかを返す（`{ ok: true }`、またはしなかった理由を付けた `{ ok: false, reason }`。理由は、記録が違う・`ref` が見つからない・NG なのに `actual` が無い・記録が変わっていた）。サイドパネルは、表示していた記録の `revision`（今もある、記録が変わるたびに進む番号）も送り、worker は今の `revision` と違えば更新しない（ほかのパネルが先に変えた判定や `actual` を、古い画面からの更新で上書きしないため。ステップが届いて変わったときも拒否されるので、パネルは読み直して、テスターがもう一度送る。自動で送り直さない）。停止も同じ。
- 記録を変える更新は、どれも `revision` を進める: 判定・`actual` の更新、停止（`endedAt`・`notTested`）、`trimmed` が強まったとき、開始時の `scope`・`targetVersion`。プレビューや下書きが古いかどうかは今も `recording.id` と `revision` で判定しているので（`sidepanel/sidepanel.js` の `basisOf`）、進めないと、変わる前のプレビューの JSON をそのまま送れてしまう。サイドパネルは返事を待ち、どちらの場合も保存された記録を読み直して表示する（先に成功と表示しない）。停止も同じ。判定は OK・NG・未判定のどれにも変えられる。NG 以外に変えるときは `actual` を消す（NG に変えるときは `actual` が要る）。
- `trimmed` は記録全体の欄で、値は `user` か `other`（無ければ欠けていない）。worker が上限のためにステップを保持できなかったとき（古いステップを消した、または新しいステップを受け付けなかった）に付ける。保持できなかったステップが `source: user` なら `user`、それ以外（遷移・通知の `unknown`、ツール呼び出し・ページからの申告の `agent`）なら `other`。値は強まるだけで弱まらない（無し → `other` → `user`。`user` から `other` や無しには戻さない）。テスターがステップを削除しても付けず、付いた値も変えない。
  - 対象の上限: ステップ数の上限で古いステップを消したとき、保存容量の上限（`fitRecord`）で古いステップか新しいステップ自体を消したとき、`fitRecord` がサイトごとの上限に合わせて消したとき、サイトごとの上限か「人のステップだけで満杯」のために新しいステップを受け付けなかったとき。形が合わない・安全の検査で落としたステップは上限ではないので対象にしない。
  - 書式 B の結論を「判定なし」にするのは `user` だけ（人の操作として記録したもの、つまり操作・期待結果・探索メモが欠けたとき）。ページは申告やツール呼び出しを大量に送れ、上限ではそれらと遷移が人の操作より先に消える（ADR 0003 の W7）ので、それらだけが欠けた `other` で結論を変えない。書式 A・B の警告は、どちらの値でも出す（遷移が欠けると再現手順の始まりが変わるため）。`source: user` はブラウザが人の操作として届けたものという意味で、テスター本人の操作とは言い切れない（W7）。
- `scope`・`targetVersion`・`notTested` は記録全体の欄で、無くてもよい。
- `endedAt` があるときは `startedAt` 以後（v4 だけで拒否する。v3 は上の表のとおり）。

判定を人だけにするのは、「確かめて問題なし」と言えるのはテスターだけだからです（ADR 0003 の W7: ページから届く申告は `agent`）。

## 出し方

- サイドパネルの **再現手順** 欄に「バグチケット」「実施記録」を足し、どちらもテンプレートで作る（AI を使わない）。今の簡易手順と Gherkin はそのまま残す。
- 送信用の JSON には、書式 A・B の文を入れない。JSON は記録そのものを持つ。書式を受け取った側で作り直すことは保証しない（文の細部は `tests/describe.test.mjs` が決め、版を上げずに変えてよい）。
- 書式 A・B は、出口の検査を通った送信データ（`buildPayload` の結果に `checkPayload` で問題が無いもの。拡張が作るので常に v4）の `recording` から作る。作った全文には、コピー・保存の直前に、今の出口と同じ `scanWith(rec)`（その時点の設定の登録語と、記録で別名にした実ホスト名を渡す `finalScan`）をかけ、検出があれば止める（AGENTS.md の「すべての出口で両方を通す」を、この新しい出口にも当てはめる）。全文は 1 つの文字列として検査するので、書式の決まり文句（「OK」「期待どおりにならない」など）と同じ語を登録していると止まる。今の簡易手順の出口と同じ既知の誤検出として扱い、検査は弱めない（止まった理由は表示する）。
- WebMCP には当面出さない。出すときは、`get_reproduction` がすでに返す範囲（そのサイトのステップ）に限る。

## 決めないこと

- 複数の記録を束ねた報告、期間ごとの集計。
- 再現率・重要度・スクリーンショットなどの添付。
- バグトラッカーへの直接の起票（コピーして貼る前提）。

## 実装の順（案）

1. ADR 0003 に `ref`・`verdict`・`actual`・`scope`・`targetVersion`・`notTested`・`trimmed` の行と、上の組み合わせの制約を足し、送信データの版を `v4` に上げる（`SHAPE`・`STEP_RULES` の `note` に `ref`・`verdict`・`actual`・受信サーバ・FORMAT・版のテスト）。
   - worker が、サイドパネルから届いた値をほかの欄と同じように作り直す: `ref` は worker が振る（届いた値は使わない。サイドパネルからの判定の更新では、指す先としてだけ使う）、`verdict` は列挙値だけ、`actual`・`scope`・`notTested` は `cleanLine`（メモと同じ伏せ方、300 字）、`targetVersion` は `cleanLine`（同じ伏せ方、80 字）。保存容量の上限（`fitRecord`）に新しい欄も入る。`actual`・`scope`・`targetVersion`・`notTested` の伏せ字は、ステップのメモと同じく `privacy.redactions` に数える。
   - `trimmed` を強める処理は 1 か所（例 `promoteTrimmed(rec, source)`）にし、ステップを捨てる `appendStep`・`fitRecord` の中で、捨てたステップの `source` を見て呼ぶ（後からは分からないため）。印を付けると記録が大きくなるので、`fitRecord` は印を付けた後の大きさで上限に収まるまで繰り返す。`appendStep`（と `addStep`）は、新しいステップを保持したかとは別に、記録が変わったか（印が強まったかを含む）を返す。呼び出し元（worker の遷移・ステップ・メモの追加・WebMCP の期待結果の追加。`service-worker.js` の `addStep` を呼ぶすべての箇所）は、新しいステップを受け付けなかったときも、記録が変わっていれば保存する。
   - 版ごとの形は 1 か所から導く: `shared/payload.js` の `SHAPE` の新しい欄に `since: 4` を書く（無ければ v3 から）。受け付ける版は `['…/v3', '…/v4']` の一覧で持ち、`SHAPE` の `schema` は 1 つの値（`const`）ではなくこの一覧の列挙値にする。v3 の形は `SHAPE` から `since: 4` の欄を除いたもの、v4 の形は `SHAPE` 全体。`checkPayload` と受信サーバは、まず `schema` を読んで一覧に無ければ拒否し、次にその版の形だけで全体を検査する（`schema` 自体はどちらの形でも一覧の列挙値で、最初の段で決まった値と同じになる。v3 の送信データに v4 の欄があれば、知らない欄として拒否する。版と欄の組み合わせを別の規則で検査しない）（除く欄の一覧を `SHAPE` の外に持たない。`checkPayload` に版ごとの許可欄を手で書かない。AGENTS.md の「送信データの形は `SHAPE` だけで定義する」を保つ）。`buildPayload` は常に v4 を作る。
   - `shared/limits.js` の `VOCAB` に `ref`（形 `^E-[0-9a-z]{6}$`）・`verdict`（`ok` / `ng`）・`trimmed`（`user` / `other`）を足す。最終検査が、登録語と同じ値（例えば登録語 `ok`）を漏れとして止めないため。
   - 新しい自由文の欄（ステップごとの `actual`、記録全体の `scope`・`targetVersion`・`notTested`）の分だけ、`shared/limits.js` のステップ・送信データの大きさの上限（`STEP`・`TOTALS`）を広げ、受信サーバの上限もそれに合わせる。最大の大きさのテストに新しい欄を入れる。
   - テスト: `tests/record.test.mjs`（worker の作り直しと組み合わせ）、`tests/payload.test.mjs`（形と拒否、v3 と v4 の両方、v3 に v4 の欄を混ぜたものと一覧に無い版の拒否、最大の大きさ、登録語が `ok`・`ng`・`user`・`other` や `ref` と同じ値でも `verdict`・`trimmed`・`ref` の値で出口が止まらない）、書式を作って検査する関数のテスト（全文に登録語や別名にした実ホスト名が入ったとき、また送信データが `checkPayload` を通らないとき、文を返さず検出を返す）、`tests/describe.test.mjs`（書式 A・B の全欄・`navigate → NG` の再現手順が「{URL} を開く」の 1 行になること・通知の対応付け（`click → tool → notice → NG`、先に操作の無い `notice → NG`、`navigate(A) → notice → navigate(B) → notice → NG` で B の通知だけ）、NG 2 件で 2 枚・結論の表の各行・ID・区切り・付録。`trimmed` の記録、`trimmed` が `other` の記録（警告は出て、結論は判定から決まる）と `user` の記録（結論が「判定なし」、NG があれば「問題あり」が優先）を、NG・期待結果なし・未判定・全 OK と組み合わせた表、NG の期待結果が上限で消えた記録、途中のステップだけが消えた記録、新しいステップを上限で受け付けなかった記録、操作・ツール呼び出し・ページからの申告の数え分け、記録 ID の表示）。`tests/record.test.mjs` に、残っているステップと重なる ID を引き直すこと、別の記録の ID を付けた判定の更新と停止を無視すること、判定の遷移（未判定・OK・NG の相互）と NG 以外に変えたときに `actual` が消えること、更新しなかったときに `ok: false` と理由を返すこと、`actual` の無い NG への更新で元の判定と実際の結果が残ること、`revision` が今と違う判定の更新と停止を拒否すること（同じ NG のまま `actual` だけを別のパネルから変える場合を含む）、判定・`actual`・停止・`trimmed` の強まりで `revision` が進むこと、`trimmed` の付き方（ステップ数の上限で `other` だけ／`user` が消える、保存容量の上限で新しいステップ自体・古い `other`・古い `user` が消える、サイトごとの上限で拒否すると `other`、`fitRecord` のサイトごとの補正で `other`、`other` から `user` へは強まり逆は無い、テスターの削除では付かず付いた値も変えない、受け付けなかったときも印が強まれば保存される（WebMCP の期待結果の追加・遷移・ステップ・メモのどの経路でも）、印を付けた後も保存容量に収まる）、新しい自由文の欄の伏せ字が `privacy.redactions` に数えられること。
2. サイドパネル（停止のときに送る「やっていないこと」には、判定の更新と同じく表示している記録の ID を付け、worker は今の記録と一致するときだけ停止して書き込む）: 開始時の「対象と範囲」「対象のバージョン」、期待結果の OK / NG と実際の結果、停止時の「やっていないこと」。
3. `shared/describe.js` に書式 A・B の生成を足す（決まった手順。テストで全欄を確かめる）。サイドパネルのコピー・保存は、検査済みの送信データから作り、全文に `finalScan` をかけてから出す。作って検査するまでを 1 つの関数（`shared/` に置く。記録・設定の登録語・別名にした実ホスト名を受け取る）にし、`checkPayload` か `finalScan` で検出があれば文を返さず検出だけを返す。サイドパネルは、その関数が文を返したときだけクリップボードに書く・保存する。書式 A の「実際の結果」と書式 B の「確かめたこと」の通知もここで入れる。
