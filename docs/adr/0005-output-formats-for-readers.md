# 0005 読み手ごとの出力の書式（バグチケットと実施記録）

- 状態: 採用（オーナー 2026-11-02。実装は未着手）
- 日付: 2026-11-02
- 関連: Issue #42、ADR 0003（保証の表）、PR #45（操作後の通知）。受動記録の範囲（ADR 0004）は別のブランチで作業中で、この ADR はそれに依らない

## 背景

op-scribe の出力は今、簡易手順（Markdown）・Gherkin と属性表・送信用の JSON の 3 つです。どれも「記録した操作を並べたもの」で、誰が何のために読むかを前提にしていません。

使う側の目的は次の 3 つです（オーナー、2026-11-02）。

| 目的 | 読み手 | 知りたいこと |
| --- | --- | --- |
| 1. 不具合の再現方法を伝える | 開発者 | どうすれば同じことが起きるか、何が期待と違ったか |
| 2. テスト活動を評価する | 上長 | 何を、どこまで、どう試したか、何が見つかったか |
| 3. 問題が無かったときの根拠を残す | 上長・PdM・開発チーム | 何を確かめて問題なしと判断したか、何はやっていないか |

2 と 3 は、問題があったかどうかで結果の欄が変わるだけで、見せるものは同じです。そこで出力の書式を、**バグチケット**（目的 1）と**実施記録**（目的 2・3）の 2 つにします。

## 決めたこと（オーナー判断 2026-11-02）

- バグチケットの欄は「概要」「再現手順」「期待結果」「実際の結果」「環境・対象バージョン」。再現率・重要度・添付は持たない。
- 実施記録は 1 回の記録（開始から停止まで）ごとに 1 つ。複数の記録を束ねるのは、人が別の場所で行う。
- 期待結果ごとに判定（OK / NG）を付ける。
- 「対象と範囲」と「対象のバージョン」は記録を始めるときに、「やっていないこと」は止めるときに、テスターが書く（どれも空欄でよい）。
- チケットと実施記録の対応は、期待結果ごとの変わらない短い ID で取る。
- NG にするときは「実際の結果」を必須にする。
- 送信データを v4 に上げても、受信サーバは v3 も受け付ける。
- 書式 A・B は拡張の中だけで作る。受け取る側には記録（JSON）だけを渡し、同じ文を作り直せることは保証しない（オーナー判断 2026-11-02、仕様を小さくするため）。

## 書式 A: バグチケット

NG と判定した期待結果 1 つにつき 1 枚。記録の中に NG が 2 つあれば 2 枚作れる。記録中でも作れる（NG を見つけたその場で起票できる）。

| 欄 | 作り方 |
| --- | --- |
| 概要 | 決まった型「[{ID}] 『{期待結果}』が期待どおりにならない（{画面}）」。{ID} は下の「チケットとの対応」の ID。{画面} は下の「期待結果の位置」で決まる伏せた URL（無ければ「画面不明」）。期待結果の文を否定形に言い換えることはしない（決まった手順では正しく言い換えられないため）。テスターが書き換える前提の下書き |
| 再現手順 | 記録の始めから、NG の期待結果の直前のステップまで（下の「期待結果の位置」）。今の簡易手順と同じ文（テンプレート）。伏せた入力は「‹任意の文字列 6文字›」のように、用意する値として書く |
| 期待結果 | NG の期待結果の文 |
| 実際の結果 | NG を付けるときにテスターが書く文（新しい欄、NG では必須）。PR #45 が入れば、そのステップの後に画面に出た通知も添える |
| 環境・対象バージョン | ブラウザ・OS・言語（今の `environment`）と、記録を始めるときに書いた対象のバージョン |

### 期待結果の位置

期待結果のメモは、ステップの並びの中の位置で、直前の操作に付く（今の簡易手順・Gherkin と同じ）。どの操作に付くかを指す欄は持たない（期待結果そのものを指す `ref` は下の「チケットとの対応」）。

- 再現手順は、そのメモより前にあるステップを、今の簡易手順と同じ規則で文にしたもの。操作の直後の遷移は、再現する人の操作ではなく結果なので、手順にせず畳む。連続する同じ URL の遷移は省く。期待結果・探索メモ・ページからの申告の期待結果は手順に入れない。操作の後に画面に出た通知（PR #45）も手順に入れず、「実際の結果」にだけ添える。
- 画面は、そのメモより前で最も近い、URL を持つステップの URL。
- テスターがステップを削除したときは、残ったステップから作る（削除は意図したものとして扱う）。
- 記録に `trimmed`（上限のために worker がステップを保持できなかった印。下の組み合わせの制約）があるとき、または先頭のステップが `navigate` でないとき（テスターが先頭を削除した）は、再現手順の先頭に「記録の一部が欠けている可能性がある」と書く（上限で消えるのは先頭とは限らない）。テスターが先頭から途中の `navigate` までを削除した場合は検知できない（削除は意図したものとして扱う）。
- メモより前に操作のステップが 1 つも無ければ、再現手順は「（記録された操作なし）」とする。

再現できる確かさ（Issue #42 の slice 3 の再生前のチェック）は、できたあとに「再現手順」の後ろへ注意として足す。

## 書式 B: 実施記録

1 回の記録につき 1 つ。記録を止めてから作る（終了の時刻と「やっていないこと」が決まってから）。記録中は作れない。

| 欄 | 作り方 |
| --- | --- |
| 対象と範囲 | 記録を始めるときにテスターが書いた文 |
| 対象のバージョン・環境 | 書式 A と同じ |
| 実施した時間 | 開始と終了の時刻を、記録の値（UTC の ISO 形式）のまま出し、差を分（切り捨て）で添える。`endedAt` が無い、または `startedAt` より前なら、実施記録は作らない |
| 実施した操作 | 画面ごとの流れ。通った画面（伏せた URL）を順に並べ、それぞれで 3 種類を分けて数える。①記録された操作: `source: user` で種類が `click` `input` `select` `check` `upload` `key` `submit`。見出しは「記録された操作（ブラウザが人の操作として届けたもの）」とし、テスターの操作だと言い切らない（ページのスクリプトも `focus()` などで同じ印のステップを作れる。ADR 0003 の W7 の既知の限界）。②ツール呼び出し: 種類が `tool`（エージェントがページのツールを呼んだもの）。③ページからの申告: 種類が `note` で `source: agent`（ページが送った期待結果）。②③は①に数えない。遷移とテスターのメモは数えない。操作の全文は付録に回す |
| 確かめたこと | テスターが書いた期待結果（`source: user`）の一覧を記録の順に。それぞれに ID・画面・判定（OK / NG / 未判定）と、NG なら実際の結果。NG のものは「バグチケット [{ID}]」と書く（下の「チケットとの対応」）。ページが申告した期待結果は判定の対象にせず、「ページからの申告」に回す |
| 見つけたこと | 探索メモ（不具合・疑問・気づき・次に試す）を種類ごとに |
| やっていないこと | 記録を止めるときにテスターが書いた文 |
| 結論 | テスターが書いた期待結果の判定と `trimmed` から、下の「結論の決め方」で作る。`trimmed` があれば、実施記録の冒頭にも「記録の一部が上限で消えている（操作の数・画面・付録も一部）」と書く |

### 結論の決め方

上から順に当てはめ、最初に当たったものにする（OK・NG・未判定は、テスターが書いた期待結果の件数）。

| 条件 | 結論 |
| --- | --- |
| NG が 1 件以上 | 「問題あり（NG n 件）」。未判定があれば「（未判定 m 件）」、`trimmed` があれば「（記録の一部が欠けている）」を後ろに足す |
| `trimmed` がある | 「判定なし（記録の一部が欠けている）」。消えたステップに NG や未判定があったかは分からないので、「問題なし」とは言わない |
| 期待結果が 0 件 | 「判定なし（期待結果が無い）」 |
| 未判定が 1 件以上 | 「判定なし（未判定 m 件）」 |
| ほか（全部 OK） | 「確かめた範囲で問題なし（OK n 件）」 |

### チケットとの対応

テスターが書いた期待結果（`note`・`kind` 無し・`source: user`）に、足したときに worker が短い ID（`ref`、`E-` と英小文字・数字 6 文字。例 `E-7f3a9k`）を付ける。ID は乱数（`crypto.getRandomValues`）で、今の記録に残っているステップの ID と重なれば引き直す。振った ID の履歴は持たない（約 22 億通りなので、削除や上限で消えた ID と同じものが同じ記録で出ることは実際上ない）。順番や件数を表さない（連番にしない）ので、ほかの期待結果を削除しても変わらない。記録をまたぐと同じ ID があり得るので、対応は「記録 ID ＋ ID」で取る: バグチケットの末尾と実施記録の冒頭に記録 ID（今の送信データの `recording.id`）を出し、ID は両方の行に出す。

### 画面ごとの流れと付録

- 区切りは記録の順に作る。URL を持つステップが直前の区切りと違う URL を持つとき、新しい区切りを始める（A → B → A は 3 つの区切り。同じ URL でもまとめない）。
- URL を持たないステップは、その時点の区切りに入る。最初の URL より前にあれば、先頭の「画面不明」の区切りに入る。
- 各区切りには、そこで数えた操作の数を出す。0 件の区切りも出す（遷移しただけの画面も通った画面として見せる）。
- 付録は、記録の順に 1 ステップ 1 行の一覧。ステップを 1 つも省かず、まとめもしない（今の簡易手順は期待結果を前の操作にまとめ、遷移を畳み、探索メモを別の節に移すので、付録には使わない）。各行は「{順番}. {ステップの文}」で、文は今のテンプレートの 1 ステップの文と同じ。ページからの申告には「（ページからの申告）」、メモには「（期待結果: OK / NG / 未判定）」か探索メモの種類を付ける。

操作の数は欄に出すが、評価の指標としては扱わない（数を増やすこと自体が目的になりやすく、テストの質を表さないため）。

## 記録に足す欄

どれも、先に ADR 0003 の表に行を足し、`shared/payload.js` の `SHAPE` に入れてから出す。今の `op-scribe.recording/v3` は知らない欄を拒否するので、欄を足すときに版を `v4` に上げる（受信サーバ `tools/receiver.mjs`・`docs/FORMAT.md`・版のテストも合わせて直す）。受信サーバと `checkPayload` は v3 も受け付ける。検査は版ごとに分ける:

| 制約 | v3 | v4 |
| --- | --- | --- |
| 新しい欄（`ref`・`verdict`・`actual`・`scope`・`version`・`notTested`・`trimmed`） | 1 つでもあれば拒否 | 下の組み合わせの制約で検査 |
| テスターが書いた期待結果に `ref` が必須 | 適用しない | 適用する |
| `endedAt` が `startedAt` 以後 | 適用しない（これまでどおり受け付ける） | 適用する（拒否） |

受け付ける版は `v3` と `v4` の 2 つだけ（`shared/payload.js` に一覧として書く）。v3 の形は、`SHAPE` から `since: 4` の欄を除いたもの。書式 A・B は拡張が今の記録（常に v4）から作るので、v3 から書式を作る処理は持たない。

| 欄 | どこに | 誰が書くか | 伏せ方（案） |
| --- | --- | --- | --- |
| 期待結果の ID `ref` | 期待結果のメモ（`kind` の無い `note`、`source: user`） | worker が足したときに振る | 決まった形 `^E-[0-9a-z]{6}$`（T6） |
| 判定 `verdict`（`ok` / `ng`） | 期待結果のメモ（`kind` の無い `note`） | サイドパネルで人だけ（`source: user`）。WebMCP のエージェントが足した期待結果には付けられない | 決まった値（T6） |
| 実際の結果 `actual` | NG の期待結果のメモ | 人だけ | メモと同じ（T1: 300 字・1 行・できる限りの検出） |
| 上限で欠けた印 `trimmed`（`true` だけ） | 記録全体 | worker が付ける | 決まった値（T6） |
| 対象と範囲 `scope` | 記録全体 | 人が開始時に | メモと同じ（T1） |
| 対象のバージョン `version` | 記録全体 | 人が開始時に | メモと同じ（T1）。80 字 |
| やっていないこと `notTested` | 記録全体 | 人が停止時に | メモと同じ（T1） |

欄の組み合わせの制約（ADR 0003 の行に書く。worker は合わない値を落として作らず、`checkPayload` と受信サーバは合わないものを拒否する）:

- `verdict` は、種類が `note`・`kind` が無い・`source: user` のステップにだけ付く。
- `ref` は、テスターが書いた期待結果（`note`・`kind` 無し・`source: user`）すべてに必ず付き（判定の前から）、ほかのステップには付かない。記録の中で重ならない。
- `verdict` は `ref` を持つステップにだけ付く（無ければ未判定）。
- `actual` は `verdict: ng` のステップに必ず付き、ほかのステップには付かない。伏せた後の文を描いて前後の空白を除いたものが空なら、付いていないものとして扱う（worker・`checkPayload`・受信サーバのどこでも同じ）。worker は `actual` の無い `ng` を判定なしに戻す。
- 判定の更新: サイドパネルは、表示している記録の ID（`recording`）と `ref` で期待結果を指して `verdict`・`actual` を送る。worker は `recording` が今の記録の ID と一致するときだけ、その記録から `ref` のステップを探して更新し、`ref` 自体は書き換えない（並びの位置では指さない。記録中に削除や上限でステップが消えても、別のステップを更新しないため。記録の ID を付けるのは、止めて新しい記録を始めたあとに古い画面から届いた更新を、新しい記録の同じ ID のステップに当てないため）。一致しない、または見つからなければ何もしない。
- `trimmed` は記録全体の欄で `true` だけ（無ければ欠けていない）。worker が上限のためにステップを保持できなかったとき（古いステップを消した、または新しいステップを受け付けなかった。ステップ数・保存容量・サイトごとの申告の上限のどれでも）に付け、外さない。
- `scope`・`version`・`notTested` は記録全体の欄で、無くてもよい。
- `endedAt` があるときは `startedAt` 以後（v4 だけで拒否する。v3 は上の表のとおり）。

判定を人だけにするのは、「確かめて問題なし」と言えるのはテスターだけだからです（ADR 0003 の W7: ページから届く申告は `agent`）。

## 出し方

- サイドパネルの **再現手順** 欄に「バグチケット」「実施記録」を足し、どちらもテンプレートで作る（AI を使わない）。今の簡易手順と Gherkin はそのまま残す。
- 送信用の JSON には、書式 A・B の文を入れない。JSON は記録そのものを持つ。書式を受け取った側で作り直すことは保証しない（文の細部は `tests/describe.test.mjs` が決め、版を上げずに変えてよい）。
- 書式 A・B は、出口の検査を通った送信データ（`buildPayload` の結果に `checkPayload` で問題が無いもの。拡張が作るので常に v4）の `recording` から作る。作った全文には、コピー・保存の直前に `finalScan` をかけ、検出があれば止める（AGENTS.md の「すべての出口で両方を通す」を、この新しい出口にも当てはめる）。全文は 1 つの文字列として検査するので、書式の決まり文句（「OK」「期待どおりにならない」など）と同じ語を登録していると止まる。今の簡易手順の出口と同じ既知の誤検出として扱い、検査は弱めない（止まった理由は表示する）。
- WebMCP には当面出さない。出すときは、`get_reproduction` がすでに返す範囲（そのサイトのステップ）に限る。

## 決めないこと

- 複数の記録を束ねた報告、期間ごとの集計。
- 再現率・重要度・スクリーンショットなどの添付。
- バグトラッカーへの直接の起票（コピーして貼る前提）。

## 実装の順（案）

1. ADR 0003 に `ref`・`verdict`・`actual`・`scope`・`version`・`notTested`・`trimmed` の行と、上の組み合わせの制約を足し、送信データの版を `v4` に上げる（`SHAPE`・`STEP_RULES` の `note` に `ref`・`verdict`・`actual`・受信サーバ・FORMAT・版のテスト）。
   - worker が、サイドパネルから届いた値をほかの欄と同じように作り直す: `ref` は worker が振る（届いた値は使わない。サイドパネルからの判定の更新では、指す先としてだけ使う）、`verdict` は列挙値だけ、`actual`・`scope`・`notTested` は `cleanLine`（メモと同じ伏せ方、300 字）、`version` は `cleanLine`（同じ伏せ方、80 字）。保存容量の上限（`fitRecord`）に新しい欄も入る。
   - 版ごとの形は 1 か所から導く: `shared/payload.js` の `SHAPE` の新しい欄に `since: 4` を書く（無ければ v3 から）。受け付ける版は `['v3', 'v4']` の一覧で持ち、v3 の形は `SHAPE` から `since: 4` の欄を除いたもの、v4 の形は `SHAPE` 全体（除く欄の一覧を `SHAPE` の外に持たない。`checkPayload` に版ごとの許可欄を手で書かない。AGENTS.md の「送信データの形は `SHAPE` だけで定義する」を保つ）。`buildPayload` は常に v4 を作る。
   - `shared/limits.js` の `VOCAB` に `ref`（形 `^E-[0-9a-z]{6}$`）と `verdict`（`ok` / `ng`）を足す。最終検査が、登録語と同じ値（例えば登録語 `ok`）を漏れとして止めないため。
   - 新しい自由文の欄（ステップごとの `actual`、記録全体の `scope`・`version`・`notTested`）の分だけ、`shared/limits.js` のステップ・送信データの大きさの上限（`STEP`・`TOTALS`）を広げ、受信サーバの上限もそれに合わせる。最大の大きさのテストに新しい欄を入れる。
   - テスト: `tests/record.test.mjs`（worker の作り直しと組み合わせ）、`tests/payload.test.mjs`（形と拒否、v3 と v4 の両方、最大の大きさ）、`tests/describe.test.mjs`（書式 A・B の全欄・結論の表の各行・ID・区切り・付録。`trimmed` の記録、NG の期待結果が上限で消えた記録、途中のステップだけが消えた記録、新しいステップを上限で受け付けなかった記録、操作・ツール呼び出し・ページからの申告の数え分け、記録 ID の表示）。`tests/record.test.mjs` に、残っているステップと重なる ID を引き直すこと、別の記録の ID を付けた判定の更新を無視すること。
